Data flow — after merge
-----------------------

Live game with CTS connected:

  CTS console (RS-232)
      │
      ▼
  CtsBridge (player page on Beelink kiosk)
      • Web Serial reader → @cms/scoreboard-cts parser
      • Throttled at 5 Hz
      • POST { clockMs, clockRunning, segment, homeScore, awayScore,
               shotClock?, horn?, raw } with x-feed-token
      ▼
  POST /api/v1/sports/board/:gameId/cts-snapshot
      • Verify HMAC feed token + rate-limit
      ▼
  SportsService.ingestCtsSnapshot()
      • Write Game.stats.cts = { lastUpdateAt: <iso>, ...fields }
      • Invalidate board cache
      • Audit-log on forensically interesting transitions
      ▼
  GET /api/v1/sports/board/:gameId  (public poll, 750 ms)
      • Returns whole Game including stats.cts
      ▼
  Board / Ribbon / Scorebug routes (public, no auth)
      • applyCtsOverlay(data) merges stats.cts onto top-level
        score/clock/segment WHEN heartbeat < 5 s old
      • Identical helper, identical math on all three surfaces


Live game with CTS stale (cable yank / console power-cycle):

  • Last snapshot in Game.stats.cts is older than 5 s
  • applyCtsOverlay returns data unchanged
  • The persistent operator-input columns (clockMs, clockRunning,
    segment, homeScore, awayScore) are rendered as-is
  • Operator's +/- chips and clock buttons in the Run console
    continue to write to those columns via the existing endpoints
  • The moment CTS reconnects (first fresh snapshot), the board
    snaps back to CTS data on the next 750 ms poll boundary


Security
--------

  • Public ingest endpoint is HMAC-gated by the per-game feed token,
    same auth model the existing `/feed` endpoint already uses.
  • Authed sibling endpoint reuses the standard JwtAuthGuard +
    CONTRIBUTOR+ role gate.
  • Rate-limit: 40 POSTs / 10 s per game on the public endpoint —
    a misbehaving bridge can't pump unbounded writes.
  • Every accepted snapshot writes to AuditLog on forensically
    interesting transitions; the cron consistency-check that scans
    `stats.cts.lastAuditAt` lag can flag a runaway bridge in
    operations dashboards.
  • Snapshot input is sanitized (`cleanCtsSnapshot()` — non-negative
    integers, capped segment >= 1, bool coercion on flags, 96-byte
    cap on the raw clock string). No injection surface.


What the operator will see after merge
--------------------------------------

  1. Open `/<schoolId>/sports/<gameId>` (Setup mode).
     A new "CTS scoreboard console" section shows a status pill that
     reads "CTS not configured" until a kiosk starts pushing.

  2. Open `https://<player>/player?cts=1&game=<gameId>&feedToken=<token>`
     on the Beelink. (The token comes from
     `GET /api/v1/sports/games/<gameId>/feed-credentials`; the existing
     "Score feed" copy button in the dashboard generates it.) Wire the
     CTS console + USB-RS232 dongle, click Connect.

  3. Within ~1 second the status pill flips to "CTS connected —
     receiving" (green pulse). The /board/<gameId> and /ribbon/<gameId>
     tabs render the live CTS clock / score / period.

  4. If the operator hits the +/- chip in the Run console while CTS
     is connected, the score column update lands but is INVISIBLE on
     the public surfaces — the CTS overlay wins. (Working as intended:
     CTS is the source of truth during a live game.)

  5. Pull the dongle. Within 5 s the pill flips to "CTS stale — using
     operator inputs" (amber). The +/- chips become live again — the
     board snaps to the operator-input values.

  6. Plug it back in. Within the next ~1 second the pill returns to
     fresh and CTS takes over again. No operator action needed.

  7. Legacy kiosks that open `/player?cts=1` WITHOUT `game=` and
     `feedToken=` continue to use the WS-broadcast path — the in-page
     CtsScoreboard widget keeps working for the existing pilot install
     without any required reconfiguration.

Out of scope (deliberately deferred)
------------------------------------

  • Prisma schema column. Per the live-pilot rule, schema migrations
    are additive-only and we use the existing `Game.stats` JSON field
    (same pattern as `stats.shotClock` and `stats.penalties` already
    in production).
  • Auto-celebrate via score delta detected from CTS data. The score
    delta in `stats.cts` doesn't fire `maybeAutoCelebrate` today — the
    existing AUTO path fires only on `Game.homeScore/awayScore` writes
    via `ingestByFeed`. Adding AUTO from `stats.cts` is a clean
    follow-up: tap into `ingestCtsSnapshot` after the write, compute
    delta vs `prevCts.homeScore/awayScore`, call the same
    `maybeAutoCelebrate` helper.
  • Per-screen CTS bridge dispatch. The CtsBridge currently mounts
    on the player kiosk; a future enhancement could let the operator
    run the bridge directly in their dashboard browser. Both endpoints
    already accept that mode (`/games/:id/cts-snapshot` uses the
    operator's JWT) — only the UI is missing.
