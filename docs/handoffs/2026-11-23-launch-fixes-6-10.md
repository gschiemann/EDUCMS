## 6. SDW-01: a device principal belongs to a tenant

**What the code now requires.**
- On `JwtAuthGuard` routes, `DeviceIdentityInterceptor` answers a device principal whose live `Screen` row has no tenant with 401 `DEVICE_SCREEN_UNPAIRED`.
  - The exception is a route that carries `@AllowUnpairedDevice()` (`apps/api/src/security/allow-unpaired-device.decorator.ts`).
  - A context that names no handler is refused.
- Three routes carry the marker. Each one reads only the screen's own row, and answers "nothing" when there is no tenant:
  - `GET /api/v1/screens/:id/manifest`
  - `GET /api/v1/emergency/messages`
  - `GET /api/v1/emergency/status`

  The decision table, with each route's client call site, is `UNPAIRED_ALLOWED` in `apps/api/src/screens/device-principal-routes.spec.ts`.
- Pairing does not run on this surface. Register, the pairing status heartbeat, unpair and the other pairing-time calls use explicit device auth with `allowUnpaired`, and none of them changed.
- A paired screen always has a tenant on its live row, so this change does not affect it. Its credential lifecycle and its emergency manifest are unchanged.
- Each handler a screen credential reaches that puts the principal's tenant into a query now requires a tenant itself, through `hasTenantId` in `apps/api/src/auth/require-tenant.ts`:
  - social posts answer empty, and the connection summary answers null;
  - asset playback answers 404, and its `where` always carries `tenantId`;
  - the Google Reviews per-tenant cap always runs (403 `GOOGLE_REVIEWS_NO_TENANT`);
  - the render capability is minted only for a tenant (403 `PROXY_CAPABILITY_NO_TENANT`);
  - touch-event ingest refuses with 403;
  - `branding/me` answers null.
- `DEVICE_SCREEN_UNPAIRED` is not a credential-recovery signal for the player (`docs/spec/SECURITY_BASELINE.md` §2).

**Why.** Every handler behind the guard can rely on a device principal's `tenantId` being a real tenant. Each handler also checks for itself, so a later change to the interceptor cannot undo that. The detail is in `docs/handoffs/2026-11-23-sdw-01-device-tenant.md`.

## 7. SDW-02: the scoreboard game-state route is bounded

**What the code now requires**, in this order, before anything is signed or published:
1. **Size.** The body is at most 16 KB. `apps/api/src/screens/game-state-body.ts` mounts a route-scoped JSON parser from `main.ts`, ahead of the global 5 MB parser. Its path match is case-insensitive. The handler re-checks `Content-Length`. Either check answers 413 `SCREEN_GAME_STATE_BODY_TOO_LARGE`.
2. **Shape.** The snapshot has the documented shape and bounds (zod, `apps/api/src/screens/game-state.ts`). A listed field of the wrong type or out of range gets 400 `SCREEN_GAME_STATE_SNAPSHOT_INVALID`. Unlisted keys are dropped, and only the parsed copy is signed and published.
3. **Credential.** The credential is a device credential for a paired screen (`allowUnpaired: false`).
4. **Rate.** At most 1200 requests per minute per client address (`@Throttle`). The route left the device-keyed throttle list. The 16 Hz per-screen floor still applies.

The order is cheapest-first on purpose. A 413 or a 400 depends on the body alone, and says nothing about the screen or its credential.

**Why.** The route publishes on the screen's Redis channel, so it is bounded like the other device write routes.

**Sizing.** The bounds come from measurements:
- Real bodies are 311-579 bytes.
- The bridge posts at most 5 Hz.
- The only caller is the scoreboard bridge in the player page, which mounts only on a paired screen in every bundle.
- 1200 per minute is four bridges at full rate behind one address, the same headroom as the bound-console route.

**Unchanged:** the message type, the signing key, the channel and the response shapes.

## 8. FLT-02: field builds only to bench screens, and an unset list fails closed

**What the code now requires.**
- **Bench list.** `fieldBenchVerdict` in `apps/api/src/player-ota/fleet-push-policy.ts` reads `PLAYER_FIELD_BENCH_SCREENS`. With the variable unset or blank, no screen is a bench screen. Before 2026-11-23, an unset list meant no restriction. The owner approved this default change on 2026-11-23.
- **Update check.** A screen is a field target only if it is inside an armed field window and on the bench list. Any other screen inside a window is answered from the stable ladder, exactly as if no window existed: operator and bulk "Send update", automatic offers, panel taps, canary, maintenance window and the emergency hold all apply. The check logs `[ota] field-window-not-bench … reason=no-bench-list|not-listed`.
- **Field push.** The SUPER_ADMIN field push (`/super/field-builds`) refuses every screen that is not a bench screen with the existing 422 `FIELD_BUILD_SCREEN_NOT_BENCH`, which is already worded in en, es and zh. It arms nothing, and it logs `[field-builds] push refused … reason=…`.
- **Download ticket.** The private field download ticket is neither minted nor honoured for a screen that is not a bench screen.
- **Screens already on a field build.** Such a screen is offered stable as soon as stable is newer by `semverGte`. A field build sorts below the stable release of the same version.
- **Listed screens** behave exactly as before.

**Why.** The owner's rule is that field builds go only to bench screens. Until now it held only if the variable had been set.

**Unaffected.** The server only changed: no APK change, and the Manager lane and canary auto-promote are unaffected.

## 9. Sentry: browser error reporting starts

**What the code now requires.**
- **Where it starts.** The browser Sentry SDK starts in `apps/web/src/instrumentation-client.ts`, the file Next runs on every page before hydration. The browser init used to sit in `apps/web/sentry.client.config.ts`, a file the Turbopack build never loads, so it never ran. That file is removed.
- **Operator pages** keep the former options, built in `apps/web/src/lib/sentry-client-options.ts`: `tracesSampleRate` 0.1, no replay, and the shared `sentry-scrub` hooks on events, transactions and breadcrumbs.
- **Screens** (`/player`, `/board`, `/ribbon`, `/scorebug`, `/overlay`) send error events only:
  - no release-health session, no tracing (so no trace headers on the screen's own requests) and no client reports;
  - at most 20 events per tab session.

  A screen gains no periodic request, and the request budget is unchanged.
- **Fetch errors** keep the message the browser wrote (`enhanceFetchErrorMessages: 'report-only'`), so the player's error classifier still reads the same text.
- **No DSN.** With `NEXT_PUBLIC_SENTRY_DSN` unset at build time there is no SDK, just one console warning per page.
- **Init failure.** An init that throws is swallowed, so a page always boots.
- **Release** falls back to `NEXT_PUBLIC_BUILD_SHA`, the deploy commit.
- **Build check.** `apps/web/tools/check-client-sentry.cjs` checks a build: the init must be in the root chunks every page loads, and every chunk `/player` loads first must parse at ES2020, the Chromium-83 floor of the Taurus LED controllers.

**Two decisions for the owner ride with this fix**, each in its own commit:
- `d098387e2` raises the summed bundle ceiling `totalBytes` from 20,400,000 to 20,600,000. Without it, the required "Web typecheck + build" check fails on the bundle budget step. The per-chunk ceilings are unchanged and pass.
- `2f43952ae` adds the check-client-sentry step to the "Web typecheck + build" job in `.github/workflows/deploy-reliability.yml`. This is a CI definition change. Dropping the commit only removes the guard.

**Measured.**
- Summed client chunks on this branch's build: 21,144,317 bytes. The old ceiling with tolerance is 21,012,000 bytes; the new one is 21,218,000 bytes.
- `/player` first-load JavaScript, raw: +165,689 bytes (+5.6 %).
- `/player` first-load JavaScript, gzip: +54,478 bytes (+6.6 %).

## 10. UXD-02: a deploy never force-reloads a visible dashboard tab

**What the code now requires.**
- **The "new version" control.** When a new SHA is deployed, the dashboard shows a small persistent control, "A new version is available", with Reload and Later, in en, es and zh. A visible tab is never reloaded on its own. Later hides the control until a different SHA is deployed.
- **When a tab reloads on its own.** Only when it has been hidden for 5 minutes and every one of these holds:
  - the route is not live: not the game console or swim bridge, not an emergency page, and not sync calibration;
  - no alert is active;
  - there is no unsaved work: the Settings shell, the classic playlist editor, the template builder, the branding logo editor, and every unfinished upload count as unsaved;
  - no overlay or dialog is open;
  - focus is not in a text field;
  - the browser is online;
  - the timer did not fire late.
- **Reading the facts.** A fact that cannot be read counts as a blocker. `freshReload` in `apps/web/src/components/layout/fresh-reload.ts` reads the facts again after the service worker answers, again before any shell cache is deleted, and again right before it navigates. The operator's Reload button always reloads.
- **Check cadence.** Checks run only while the tab is visible: 30 s after mount or after the tab becomes visible, then at most every 5 minutes. A hidden tab makes no requests.

**Why.** Before this change, a deploy reloaded an open dashboard tab after a 30-second countdown, whatever the operator was doing.

**Unaffected:** the player and its own bundle check, `/api/build-info`, and every emergency route.

## Rollback

- **Code.** Revert the merge, or redeploy the previous build. There is no migration and no data change, so the previous build runs unchanged.
- **Field-build gate.** `PLAYER_FIELD_BENCH_FAIL_OPEN=1` restores the old reading of an unset list without a deploy.
- **Browser reporting.** Unset `NEXT_PUBLIC_SENTRY_DSN` and redeploy the web.
- **Dashboard reload.** There is no switch for the dashboard reload rules; rollback is a web redeploy of the previous build.
