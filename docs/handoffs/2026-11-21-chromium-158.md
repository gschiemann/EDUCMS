# 2026-11-21: Chromium 158 in both images (CVE-2026-125350)

The lead's Friday evening check-in (fired 2026-11-21T01:30Z, Friday 7:30 PM Central). Times are UTC.

## What changed

`ARG OS_PACKAGES_REFRESHED` moves from 2026-11-17 to 2026-11-21 in `Dockerfile` and `apps/renderer/Dockerfile`, with the comment beside each. Nothing else. Moving the date makes a builder that keeps layers (Railway) fetch the OS packages again.

## Why

CVE-2026-125350 is a use after free in Chromium's XML code, exploited in the wild, fixed in 157.0.8103.50 (and in 156.0.8078.96 on the extended stable line). Both images ran 156.0.8078.79-r0, and both launch Chromium with `--no-sandbox`, because the container's seccomp profile denies the namespaces the sandbox needs.

Alpine 3.24 did not backport the 156 fix. It moved the branch to the current upstream stable instead: aports merge request 112008, "[3.24] community/chromium: upgrade to 158.0.8127.36", opened 2026-11-17. A fresh build of the API image installed 156.0.8078.79-r0 at 2026-11-20T01:33Z and 158.0.8127.36-r0 at 2026-11-21T01:31Z (the "Docker build + boot smoke test" job of Deploy Reliability run 44660067265, attempt 2). Chrome 158 reached the desktop Stable channel on 2026-11-17 with 158.0.8127.36 as the Linux build, so this is the upstream stable release, not a beta.

## What proves it works, and what does not

- **Renderer image:** the "Renderer image build + render smoke test" job builds the image and renders a real board in it: 1920 wide, Inter drawn from the bundle as a webfont, the external image blocked, text measured. It prints the Chromium version it used. That is a real test of Chromium 158 with puppeteer-core 25.13.0 in this Alpine base.
- **API image:** the "Docker build + boot smoke test" job builds and boots it, and its log prints the installed version. It does **not** launch Chromium. The API uses Chromium for two things, both in a child process: the web render path behind `/api/v1/proxy/web` and the PDF rasteriser behind imports and PDF pages. Neither is exercised in the image by CI.
- What limits the exposure of that gap: `/api/v1/proxy/web`, `/api/v1/proxy/render-capability` and `/api/v1/imports/prepare` each had **zero requests in the last 7 days** (Railway request metrics; a control query on `/api/v1/health` for a 7-day window returned 5,219, so the path filter works). The web render path falls back to fetch and strip-scripts when a render fails. Both paths use the same puppeteer-core as the renderer and nearly the same launch flags, without `--single-process`.
- `scripts/sec006-container-proof/run.sh` is the in-image proof for the web render path. It is not wired into CI and could not be run from the lead's workspace (no Docker daemon). Running it against the 158 image, or wiring it into Deploy Reliability, is the follow-up; the second is a CI definition and needs the owner's go.
- Chrome 158 is reported to remove XSLT (coverage of the 2026-11-17 release). Nothing here uses it: no `XSLTProcessor`, `xml-stylesheet` or `<xsl:` in the web app, the templates, the API or the renderer (a case-insensitive search for "xslt" matches only base64 font data in five directory boards).

## Rollback

Revert the pull request, or redeploy the previous Railway build. Either way production goes back to a Chromium with the exploited bug, so a rollback is a reason to turn the web render path off (`SSR_ENABLED=false`, offered to the owner on 2026-11-20 and not answered) until the cause is found.
