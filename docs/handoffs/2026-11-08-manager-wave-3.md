## What changed

**#10 Device-owner dead code removed (Manager).** `AdminReceiver.kt`, `res/xml/device_admin.xml`, its manifest `<receiver>` (BIND_DEVICE_ADMIN), `pinPlayerAsHome`, `allowPlayerLockTask`, and every `isDeviceOwner` branch (OtaWorker log, OtaInstaller log, `maybePromptForInstallPermission` early return) are gone. Kept: every non-DO install path (REQUEST_INSTALL_PACKAGES, UPDATE_PACKAGES_WITHOUT_USER_ACTION, InstallPromptActivity, the silent hint on Android 12+). The manifest only loses a receiver, so an install over a running screen is unaffected. Pinned by `ManagerNoDeviceOwnerTest`.
Deliberately NOT removed (outside the Manager, entangled, and gated so they are inert without DO): Player `LockTaskController` and its callers, `DeviceOwnerRebootProvider`, `PlayerApp`/`RelaunchEscalation`/`SetupCeremony`/`DisplayCapabilityProbe` "manager is device owner" probes, `PermissionFacts.MANAGER_ADMIN_CLASS`. They read `false` forever now. A follow-up wave can delete them; it touches the reboot and display waves' files, so I left it.

**#9 Strings en/es/zh.** Manager notification channel names, titles, texts and the debug/release target label moved to `values/`, `values-es/`, `values-zh/` `strings.xml`. Player: the update-ready card moved to `strings_ota.xml` (+ es, zh) because I generalised that card. `scripts/check-android-i18n-parity.cjs` (new, wired into `android-player-apk.yml`'s version-guard step) fails on a missing/extra key, differing placeholders, an empty value, a missing locale file, or a literal passed to `setContentTitle`/`setContentText`/`bigText`/`description =` in Manager Kotlin. Files carrying `tools:ignore="MissingTranslation"` (the Player's English-only `strings.xml`: pairing screen, Android device-admin descriptions) stay waived; the deep dive lists no other English-only Player strings.

**#12 Install tap on the glass.** Reality check on the premise: the Player already holds content behind a remote-operable companion gate and raises Android's Install dialog from the foreground. The gap was (a) a raise Android refuses, and (b) a screen that moves on after the gate's 3-minute hold with the companion still behind — nothing told the dashboard. Added:
- `CompanionTapPolicy` (pure, JVM-tested): card only when the raise did not take, the screen is foreground, no alert (`PendingInstallStore.emergencyHeldNow` and `DisplayEmergency.isHeld`), not in standby, not within 6 h of a person's decline, at most 2 cards per process.
- `UpdateReadyCard` reused with `forCompanion = true` (parked focus on Install, `applyRemoteFocus` highlight, Back = Not now, 1 s emergency watch, bounded window).
- `MainActivity`: `verifyCompanionPromptAppeared` after a companion raise; `reportCompanionNeedsTap` fires `NEEDS_TAP` via the same `OtaStateReporter` (device-token signed) when the card is declined or the gate releases unanswered; once per target versionCode per process, never during an alert.
- API: the message starts with "Companion service" (never "Manager v", which the server drops as noise). `companion-tap-report.ts` + a branch in `reportOtaState`: believed only from the authenticated device, ignored while a Player push is pending (so it cannot close or hold the push), otherwise stored in the ordinary status line and holds nothing.
- Autonomous behaviour record: kill switch = the existing `/sdcard/edu-cms/skip-manager.txt` opt-out (no companion work at all) plus the per-process cap and 6 h decline; no new env var. Failure direction: any doubt (staged prompt gone, alert, standby, background) shows nothing and reports nothing. `docs/ENVIRONMENT.md` not edited (no variable added); the lead may want a row for the opt-out file if it is not already there.

**#8 Clear quarantine.** `POST /api/v1/screens/:id/clear-update-quarantine` (SUPER/DISTRICT/SCHOOL admin; screen looked up in `readableTenantIds`, out-of-scope = 404, tenantless = 400). The `UPDATE_QUARANTINE_CLEARED` AuditLog row is written first and awaited (no row, no command). A signed `CLEAR_UPDATE_QUARANTINE` (scope screen) goes out on the tenant channel; the web player relays it through a new nonce-gated bridge method `clearUpdateQuarantine` (floor 1.1.66) to `PlayerApp.clearManagerQuarantine`, a signature-protected broadcast to the new Manager `ClearQuarantineReceiver`, which calls `QuarantineList.clear`. UI: `UpdateQuarantineSection` in the drawer's Actions tab (only for a screen that reported a Manager, only for admins), shared `Button`/`Alert`/`appConfirm`. Copy says "sent", never "cleared", and says plainly it is not a rollback: without device owner Android refuses to install an older version over the running one.
