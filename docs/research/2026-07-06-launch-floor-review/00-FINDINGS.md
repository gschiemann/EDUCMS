### 3. [P2] webhook-retry-reclaim (incomplete) — 8e09690a

**Reclaim treats a live-but-DB-stalled worker as crashed → double-sends an already-delivered emergency.triggered webhook**

- File: `apps/api/src/webhooks/webhook-retry.worker.ts:112`  · votes 2/2

Scenario: The reclaim's only liveness signal is `updated_at < NOW() - max(30s, reclaimMs)`. `updated_at` is set to NOW() by the CLAIM (line 146), then only re-bumped when applyOutcome's `webhookDelivery.update` lands (dispatch svc line 297). attemptDelivery is bounded at 8s (timeoutMs:8000), but the interval between the receiver actually processing the POST and applyOutcome's DB write completing is NOT bounded. Under the Prisma pool-starvation condition this codebase is documented to hit (CLAUDE.md: connection_limit too low → multi-second-to-timeout pool waits + pool_timeout=20), a worker on Replica A can successfully POST an emergency.triggered webhook (receiver side-effect done, 200 returned) but then block >30s waiting for a pool connection to write applyOutcome. Replica B's reclaim sees the stale updated_at, cannot distinguish this live-but-stalled worker from a crashed one, re-arms next_retry_at=NOW(), and the next claim re-POSTs the SAME emergency webhook to the third-party receiver — a genuine double-delivery of a life-safety alert. The fix's own comment asserts 'a live attempt updates the row within seconds' and 'never touches a row a healthy replica is actively working', but that invariant only holds when the DB write path is healthy; it breaks under exactly the pool-exhaustion failure mode this app is known for. This is at-least-once by explicit design (commit msg + comment: 'may double-send; receivers dedup by eventId'), so severity is bounded IF and only if every emergency-webhook receiver dedups on eventId — which is a third-party contract the platform cannot enforce. Default reclaimMs=120s makes the window narrow; the 30s minimum floor makes it reachable.

Evidence: AND "updated_at" < NOW() - (INTERVAL '1 millisecond' * ${Math.max(30_000, Math.floor(reclaimMs))})  — updated_at is a proxy for worker liveness, but applyOutcome's update (webhook-dispatch.service.ts:296-302) is wrapped in try/catch and its completion is unbounded under pool contention; a stalled-but-alive worker is indistinguishable from a crashed one, so the reclaim can re-arm a row whose emergency POST already succeeded.

Verifier 1: The reproduction chain holds against the actual code. The reclaim query (webhook-retry.worker.ts:106-114, NEW in 8e09690a — the parent has no reclaim logic) uses `updated_at < NOW() - max(30s, reclaimMs)` as its SOLE liveness signal. `updated_at` is set to NOW() at claim time (line 146) and is only re-bumped when applyOutcome's `webhookDelivery.update` lands (dispatch line 297, via Prisma `@updatedAt` on schema line 303) — there is no intermediate heartbeat. attemptDelivery bounds only the HTTP POST at 8s (timeoutMs:8000, line 214); the interval between the receiver completing its side-effect + returning 200 and applyOutcome's DB write landing is genuinely unbounded. Crucially, the fix's own mitigation ('receivers dedup by eventId') is weaker than the comment claims: the body payload ({tenantId,event,timestamp,data}, dispatch line 120) exposes NO field named eventId, and the header that most resembles a dedup token, X-VenueOS-Delivery-Id, is regenerated with a fresh crypto.randomUUID() on EVERY attempt (lines 199-202) — so a receiver keying dedup on the delivery id would treat each retry as distinct and NOT dedup. Verifier 2: The claim's mechanism reproduces in code. The reclaim (webhook-retry.worker.ts:106-114) uses `status='PENDING' AND next_retry_at IS NULL AND updated_at < NOW()-max(30s,reclaimMs)` as its ONLY liveness signal. `updated_at` is set by the CLAIM (line 146) and only re-bumped when applyOutcome's `webhookDelivery.update` lands (dispatch:297). That row is byte-for-byte indistinguishable from a mid-drain crash. After the window elapses, the reclaim re-arms next_retry_at=NOW(), the next claim re-POSTs the SAME already-delivered webhook (a real second HTTP send, not a no-op), and the receiver gets a duplicate life-safety alert. The fix's own comment invariant — 'a live attempt updates the row within seconds ... never touches a row a healthy replica is actively working' — is false precisely under this failure mode, because the write path can fail rather than complete.
