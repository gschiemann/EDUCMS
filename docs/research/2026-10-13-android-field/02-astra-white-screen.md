## Finding: the attempted z-order fix does not implement its claim

**Proven source defect:** `FaceVideoBox.kt:233–242` says solo video is above the page and needs no transparency, but calls `setZOrderMediaOverlay(true)`. That API places a surface above other media surfaces **while remaining behind the window**. `setZOrderOnTop(true)` instead places it above the window, where window content cannot cover it. Android permits dynamic changes with the modern target/API implementation; this APK targets 34 (`app/build.gradle.kts:16`), and the two requested classes are Android 13. Do not infer support for the older fleet from this.

Primary reference: [Android SurfaceView API](https://developer.android.com/reference/android/view/SurfaceView#setZOrderMediaOverlay(boolean)) and [setZOrderOnTop](https://developer.android.com/reference/android/view/SurfaceView#setZOrderOnTop(boolean)). Both methods override the other. No later media-overlay call may undo a promotion.

The same incorrect call exists in `e68dab3b`. This is not a source difference introduced by the current checkout.

## Causal chain consistent with brief web video → persistent white

1. `FaceVideoBox.kt:178–194` downloads/verifies and re-authorizes the exact source before attachment. `218–262` inserts a container immediately before the WebView, with a black fitted box and a SurfaceView. Protocol 2 occupies the full face; protocol 3 is parked. The solo native surface is therefore present **before** the web gives up playback.
2. Renderer `prepare()` (`FaceVideoRenderer.kt:59–88`) only inspects metadata/chooses a codec. It does not allocate or decode. `FaceVideoBox.kt:294` reports ready on that result.
3. Web `NativeDualVideo.tsx:153–180` keeps the web clip playing until its loop boundary, with a 60-second maximum. At handoff (`112–143`), it copies the last frame into a canvas if possible, releases every HTML decoder, and unmounts the video children. React's subsequent effect commits native (`231–234`). A capture failure leaves a black canvas; it does not explain indefinitely white by itself.
4. Native commit (`FaceVideoBox.kt:302–313`) makes only the WebView background transparent and starts the decoder. The web injects transparent CSS for html/body/player wrappers (`NativeDualVideo.tsx:250–253`). Neither action changes the media-overlay layer into an above-window surface. The native parent is black (`activity_main.xml:19`), the fitted box is black, and the theme has an opaque window background; ordinary SurfaceView hole-punch/composition behavior may still work on a conforming configuration. Source alone cannot identify which OEM/window/WebView layer supplies the observed white pixels.
5. MediaCodec callbacks (`FaceVideoRenderer.kt:128–130`) increment counters if the surface is valid. `FaceVideoBox.kt:379–387` promotes state to presenting when a valid callback arrives and `isShown` is true. `sessionJson:428–436` reports visible from attachment/View visibility, **not actual compositor occlusion or illuminated pixels**.
6. Web freshness (`nativeSharedVideo.ts:775–800`) accepts these progressing counters. `NativeDualVideo.tsx:193–197,245` consequently removes the retained canvas. If the native surface is hidden by the window, there is now neither web video nor a retained frame covering the blank composition.
7. Native's eight-second output-stall timer (`FaceVideoBox.kt:402`) and web's five-second freshness timer (`nativeSharedVideo.ts:809–814`) never fire while callbacks continue. Polling every 500 ms renews the ten-second page lease (`FaceVideoBox.kt:455`). Thus the renderer can remain healthy by every existing software metric while the screen stays white indefinitely.
8. Back opens the page stop menu (`MainActivity.kt:1863–1870`; page `4280–4306`), causing normal content to unmount/stop. Resume or a reload starts another attempt, reproducing the same takeover. This is consistent with remote intervention temporarily restoring output. It is not evidence of a process crash or decoder death.

**Physical cause remains unproven:** fresh Brookfield native state, frame deltas, and a timestamped physical observation are needed to distinguish hidden native output from a decoder producing white pixels, a different deployed web bundle, a main-frame error document, or an actual stall. If white occurs with stopped callbacks/failed state, follow that reason instead. Do not present historical VisionCore counters as current Brookfield measurements.

## Why a one-line setOnTop-at-attachment patch is insufficient

An above-window surface attached during prepare can cover the live web clip, hold canvas, emergency UI, and native recovery/menu views. Its decoder has not started and the web intentionally waits as long as 60 seconds before commit. This directly predicts the earlier black period and covered UI. Bringing the WebView to front in the ViewGroup cannot cover an above-window surface. Making the window globally translucent is not a minimal substitute and changes the composition contract for unrelated content.

## Smallest defensible private candidate

For **protocol 2 on the authorized Android-13 field units only**, implement a two-state composition lifecycle in `FaceVideoBox.kt`, plus explicit native UI yielding in `SharedVideoHost.kt`/`MainActivity.kt` where required:

1. Keep the SurfaceView under the window through download, prepare, the boundary wait, and initial decoder startup. Keep the existing hold-frame handoff. Do not reparent/detach/recreate the decoder surface to raise it. Do not mark takeover complete at prepare or `releaseOutputBuffer`.
2. On the first valid **render callback**, on the main thread, recheck session generation/liveness, attachment, valid surface, emergency hold, and whether operator/native overlay UI requires the window. Then call `setZOrderOnTop(true)` for this narrow path and record the native composition ownership before reporting `presenting`. Android 13 with target 34 supports the dynamic mechanism. If those conditions fail, retire the attempt and restore web. Keep the older/protocol-3 composition path unchanged.
3. Protocol-2 top mode must not depend on transparent WebView/CSS holes. Leave/reinstate the WebView's normal opaque background for this path; the video surface is independently above it. Existing web CSS may remain transparent without widening the patch, provided contain margins demonstrably stay black. Do not alter orientation, dimensions, frame rate, fit policy, source hash, or codec choice in this investigation.
4. Retirement must first mark the session dead and immediately hide/remove or lower its elevated surface **on the UI thread**, then stop the decoder asynchronously and restore the window background. When already on the main thread, do not defer visibility removal to a later posted task. Off-main callers can post the UI operation, but must not report an alert/UI-visible transition as complete before it executes. Preserve the hold check at commit, first-frame promotion, and the periodic safety watch; never release the emergency hold as part of video teardown.
5. Back/Stop and native recovery/setup/URL overlay paths must yield elevated normal video before showing their UI. Existing Back merely dispatches JS; explicit native yielding at that dispatch protects against a delayed page. Preserve emergency remote-input lockout. A playback menu toggle can resume through the existing web lifecycle; no new automatic native retry loop is needed. Make the same visibility guarantee for the raw Escape path through React unmount cleanup, and test it. If a native overlay entry point cannot be confidently covered, do not enable top mode while that overlay can appear.
6. Keep session-identity guards for delayed first-frame callbacks and queued retirement work. `surfaceDestroyed` already retires live attached sessions (`247`), and activity pause calls `SharedVideoHost.suspendAll()` (`MainActivity:4175`). Do not try to carry an old renderer over a destroyed/recreated surface. Resume should let the web controller see failure and remount browser playback; it must not resurrect a retired session. Secondary windows use the same host but are **not** qualified by testing these two primary screens.

This is a targeted lifecycle fix, not a guarantee of physical success. Add bounded diagnostics for session phase and intended layer mode so new evidence differentiates “decoded behind window” from “promoted output”; neither should be labelled physical visibility proof.

## Other source observations kept out of this patch

Protocol-3 `firstFrame()` is fired immediately after releasing an output buffer (`FaceVideoRenderer.kt:168–173`), before the render listener confirms that frame. Its pre-roll is off-screen, and `isShown` is not a test for intersection with the display. Those semantics deserve a separate protocol-3 review; changing them now confounds the solo white-screen diagnosis. The 10-second lease, 8-second output watchdog and bounded hold remain valuable but cannot detect occlusion. No evidence justifies weakening them.

The API descriptor is separately authenticated per face (`FaceVideoBox:163–175`) and the file is re-proved after download. The API's default enrollment is `faces`, with explicit IDs and exclusions (`apps/api/src/screens/native-video.ts:69–131`). Verify the actual Brookfield manifests; do not widen to `all`, all Brookfield, model-wide, or the stable 1.1.29 fleet.
