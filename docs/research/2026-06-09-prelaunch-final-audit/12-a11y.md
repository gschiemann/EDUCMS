## 1. axe-core CI baseline — ratchet is REAL, coverage is partially theater

**Verified real:**
- `.github/workflows/a11y.yml` runs on **push to master + PRs** (push added 2026-05-25 so hot-fixes can't skip the gate), builds web, boots it, runs `pnpm a11y:ci` (root `package.json:27` → `apps/web/scripts/a11y-audit.ts`).
- Errors (critical/serious) fail the build unconditionally (`a11y-audit.ts:142-145`).
- Warning ratchet: `apps/web/scripts/a11y-warning-baseline.json` = **1**, locked 2026-05-31, retiring the 999 bootstrap ceiling. `totalWarnings > warningBaseline` → exit 1 (`a11y-audit.ts:148-155`). Down-only policy documented in both the script header and the JSON note. **The ratchet is not a costume.**
- 10 routes scanned with `wcag2a/wcag2aa/wcag21a/wcag21aa` tags; `DISABLED_RULES` is empty (no silent rule suppression).

**Gap A (KNOWN-OPEN, P2): the harness runs unauthenticated.** The baseline JSON's own note says it: *"the CI harness runs UNAUTHENTICATED (no DB seed / login), so authed tenant routes render their login/shell state — this count covers public renders."* That means 7 of the 10 "flagship routes" — `/dashboard`, `/screens`, `/{tenant}/templates`, `/{tenant}/emergency/broadcast`, `/{tenant}/reviews`, `/onboarding/branding`, `/{tenant}/screens?view=map` — are axe-scanned in their **redirect/login-shell render**, not their real UI. The builder, the emergency console, the fleet map, and the dashboard have **never been axe-scanned in CI**. The note flags "auth-ing the harness + adding the builder route" as the §18 P1 follow-up (2026-05-31); 10 days later it is still open. Restating as KNOWN-OPEN rather than re-reporting.

**Gap B (NEW, P3): a failed route load silently passes.** `auditRoute()` catches `page.goto` failures and `return []` (`a11y-audit.ts:74-79`). A route that 500s, times out, or infinite-spins is counted as **zero violations** — indistinguishable from a clean pass. The only liveness assertion in the workflow is `wait-on /login` (a11y.yml:69). Combined with Gap A, the gate's effective guaranteed coverage is roughly `/login`, `/player`, `/panic`. Fix: count load failures and fail the build (or at minimum assert N routes actually rendered a non-error page).

## 2. Emergency live regions — P1-9 VERIFIED REAL (aria-live half), focus-trap half NOT present

**Verified real, traced to render sites:**
- `apps/web/src/components/emergency/EmergencyLiveRegion.tsx:69-75` — `role="status" aria-live="assertive" aria-atomic="true"` sr-only region + best-effort Web Speech (`speak()`, lines 35-62, swallows TTS failures correctly).
- **Broadcast console** (`app/[schoolId]/emergency/broadcast/page.tsx`): hook at :62, region **rendered** at :226, `announce()` on every lifecycle transition — validation fail :97, hold start :100, hold cancel :135, sending :144, dispatched :175, **failure ("your alert was NOT sent")** :185, cleared :197, clear-failed :208.
- **Trigger modal** (`components/emergency/EmergencyTriggerModal.tsx`): hook at :50, region rendered at :155, announce on type-select :187, sending :86, success :109, failure :127.
- **/panic** (mobile): inline region `role="status" aria-live="assertive"` at `app/panic/page.tsx:311-316`, announce on ready/holding/triggering/sent/failed/all-clear (:131-:299), `aria-label` on every hold button (:489). **Live-verified:** `curl https://venue-os.app/panic` returns `1× aria-live="assertive"` + `1× role="status"` in the SSR HTML.
- **Dashboard EmergencyOverlay** (`components/layout/EmergencyOverlay.tsx:95-114`): `role="alert"` on a nested wrapper + assertive/atomic, with correct WAI-ARIA reasoning in comments.
- **Keyboard-HOLD parity** — the 3-second hold is keyboard-operable on BOTH hold surfaces: broadcast page `onKeyDown/onKeyUp` handlers (:344-345) with aria-label *"Press and hold (or hold Space/Enter) for 3 seconds"* (:348); /panic `handleKeyDown/handleKeyUp` (:485-486). Key-up before 3s cancels exactly like pointer-release (:115 comment). This is better than most prior audits gave it credit for.

**Finding (NEW, P2): `EmergencyTriggerModal` is the only modal in the app without dialog semantics — and it's the life-safety one.** The root is a plain `fixed inset-0 z-[100]` div (`EmergencyTriggerModal.tsx:154`) with:
- **No `role="dialog"` / `aria-modal="true"`** — screen readers don't enter dialog mode; the entire obscured dashboard stays in the accessibility tree and reading order.
- **No focus trap** — Tab walks out of the modal into the backdrop-blurred page behind it (sidebar, toolbar). During a lockdown, a blind operator can silently tab out of the trigger flow.
- **No Escape-to-close** — only key handling is Enter-fires-trigger in the confirm field (:229-230). Note `ProfileEditModal.tsx:49` comments "Esc to close — matches the pattern in EmergencyTriggerModal", which is **inaccurate** — no Escape handler exists in the file (grep `key ===` → only :230 Enter).

Contrast with the shared primitive `components/ui/app-dialog.tsx` (role="dialog" :253, aria-modal :254, Escape :181, owned initial focus :172-178, arrow/Tab/D-pad focus movement :203-230) and with the 14 other surfaces using `role="dialog" aria-modal` (playlists :1898/:2102/:2282, screens :2245, templates :779/:1375, sports console ×4, UsbIngestCard :233, etc.). The fix is mechanical: add `role="dialog" aria-modal aria-labelledby`, an Escape handler, and the same trap pattern app-dialog uses. The 2026-06-09 REPORT's "P1-9 aria-live **+ focus trap**" claim is **half-verified**: aria-live is fully real; the focus-trap half does not exist in this modal.

What IS good in the modal: `autoFocus` on the confirm input (:236), aria-label on the close X (:171), per-type confirm words, live announcements throughout.

## 4. Fleet-map pin color-blind safety — VERIFIED REAL

`components/screens/ScreenMap.tsx`:
- `STATUS_META` (:192-196): each status gets **color + a distinct Lucide shape** — EMERGENCY `#dc2626`/AlertTriangle (+pulse), ONLINE `#10b981`/Wifi, OFFLINE `#64748b`/WifiOff, PENDING `#94a3b8`/MonitorPlay — with the explicit comment "distinct Lucide shape for WCAG 1.4.1 (color is never the only signal)" (:191).
- Each pin div carries `role="img" aria-label="{label}"` (:210); icon SVG is `aria-hidden` (:209) — correct pattern.
- Legend with counts (desktop + mobile, :35); status taxonomy deliberately simplified to 4 to keep the legend glanceable (:58).
- Red≠green confusability addressed: deuteranopia-safe via shape + pulse animation on EMERGENCY.

**Finding (NEW, P3): cluster bubbles are color-only.** The markercluster icon factory colors each cluster bubble by worst-status inside it ("red > amber > green", :20, :333-338) but the bubble content is just the count — no shape/badge distinguishes a red (emergency-containing) cluster from a green one for a color-blind operator at low zoom. Pins burst on zoom and popups carry status text, so impact is bounded; add a small worst-status glyph inside the bubble.

## 5. WCAG AA contrast guard on brand palettes — VERIFIED REAL in the adopt path

This was the highest-stakes "is it theater?" check (tenant adopts near-white/yellow primary → white-on-yellow buttons everywhere). Traced end-to-end:

- `apps/api/src/branding/color-utils.ts`: real WCAG math — `contrastRatio` (:138), `wcagGrade` (:144-148), `ensureContrast(bg, fg, target=4.5)` **binary-searches HSL lightness away from the fg's luminance until ≥4.5:1** (:191-220), `ensureBgInkContrast` (:256+).
- **Live callers, both adopt paths:** `branding.controller.ts:294` and `:1034` — `enforcePaletteContrast({ ...derivePalette(finalPrimary, finalAccent), ...(body.palette || {}) })`. Critically, the guard runs **after** the client-override spread, closing the documented past bug where `body.palette` reinstated a raw yellow that `derivePalette()` had already adjusted (:1040-1047).
- `enforcePaletteContrast` (:1052-1094): enforces 4.5:1 on `primary` and `accent` vs their ink, preserves the operator's original in `primaryRaw`/`accentRaw`, and emits a `ContrastReport` with per-color `fromRatio/toRatio/adjusted/capped` — so "what hits the DB always passes 4.5:1" and the wizard can show the operator what changed. The `capped` flag honestly records the rare can't-reach-target case instead of lying.

**Nuances (P3, informational):**
- Guard covers `primary`/`accent` ink pairs only — derived tints (`primarySoft` l=94, `surfaceAlt` l=97) are fixed high-lightness with dark ink, so safe by construction.
- The client-side mirror `components/branding/palette-client.ts` (demo page only, no auth) derives but does **not** enforce — its `bestTextOn` worst case is ≈4.3:1 on a mid-tone (~L 0.19) brand color. Demo-only blast radius; keep in mind if `derivePaletteClient` is ever reused on an authed surface.

## 6. Form labels + error announcements — labels good, inline errors silent (class finding)

**Labels:** consistently real across audited forms — login email/password/MFA (`htmlFor`, :324/:338/:260), playlist-wizard name (`htmlFor="wizard-playlist-name"`), EULA checkbox `aria-describedby="eula-text"` (:377), SSO slug label (:434).

**Error announcement — two camps:**
- **Announced (good):** broadcast console (live region :97), playlist-wizard create failure (appAlert dialog = focus move), templates AI modal (`role="alert"` :858). 14 `role="alert"` sites app-wide — the pattern exists.
- **Silent (NEW, P2):** inline conditional errors render with **no `role="alert"` / `aria-live`** so dynamically-inserted failure text is never announced:
  - **Login** — both error sites: `login/page.tsx:284-288` (MFA step) and `:401-404` (credentials step). A blind operator who mistypes a password gets *silence* — on the first-touch surface of the product.
  - **BrandingWizard** — `components/branding/BrandingWizard.tsx:571-574`, same `{error && (<div>...` pattern (this route IS in the axe ROUTES list, but axe cannot catch missing live-region semantics on not-yet-rendered content — exactly the class the P1-9 commentary warned about).
  - Sweep the class: any `{error && (` without `role="alert"` — the two above are the confirmed user-blocking ones.

Fix is one attribute per site: `role="alert"` on the error wrapper (implicit `aria-live="assertive"` + atomic).
