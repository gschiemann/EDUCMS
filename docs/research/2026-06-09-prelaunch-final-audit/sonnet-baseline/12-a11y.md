## Findings

### A-01 — P2: axe CI runs UNAUTHENTICATED only — authed-route violations invisible to gate

**Severity: P2**

The `a11y-warning-baseline.json` note (locked 2026-05-31) explicitly admits: "COVERAGE CAVEAT: the CI harness runs UNAUTHENTICATED (no DB seed / login), so authed tenant routes render their login/shell state — this count covers public renders. Auth-ing the harness + adding the builder route to ROUTES is the follow-up to widen coverage."

The 10 routes tested (`/login`, `/dashboard`, `/$SEED_TENANT/templates`, `/panic`, `/$SEED_TENANT/emergency/broadcast`, etc.) do **not** render their actual content in the CI run because there is no authenticated session. The axe check sees login redirects or empty shells, not the real template gallery, builder, screens page, or emergency console. The real violation density of the authed surfaces is completely unknown to CI.

**Evidence:** `apps/web/scripts/a11y-audit.ts:44-55` — no `storageState`/`cookies`/`Bearer` token set before navigation. `page.goto(route)` hits unauthenticated state.

**Fix:** Add a Playwright `storageState` fixture or pre-login step that authenticates as the seed tenant's `SCHOOL_ADMIN` before the audit loop. Seed tenant ID `00000000-0000-0000-0000-000000000002` already exists. Cost: ~5 lines in the script. This would expose the actual builder, gallery, screens, and playlist wizard to axe.

**Legal relevance:** ADA Title II and Section 504 require equal access for operators (not just students). An unauthenticated axe sweep does not satisfy a school district's a11y obligations for its CMS operators.

### A-02 — P2: Severity toggle buttons on broadcast page have no `aria-pressed` or `role="radio"`

**Severity: P2**

The broadcast page `severityButton()` helper (lines 212-222) renders plain `<button type="button">` elements for INFO / WARN / CRITICAL. They change visual state (`severity === s ? ... bg-orange-500` etc.) but have **no accessible state**:
- No `aria-pressed` attribute
- No `role="radiogroup"` / `role="radio"` on the container
- No `aria-checked`

A screen reader user clicking "WARN" hears "WARN" and then nothing — they cannot determine which severity is currently selected without navigating away and back.

**Evidence:** `apps/web/src/app/[schoolId]/emergency/broadcast/page.tsx:212-222` — `severityButton()` renders `<button>` with no state attribute.

**Fix:**
```tsx
// Option A: aria-pressed
<button
  aria-pressed={severity === s}
  ...
>

// Option B: promote to role="radiogroup" on the container + role="radio" + aria-checked on each
<div role="radiogroup" aria-label="Alert severity">
  <button role="radio" aria-checked={severity === s} ...>
```
Option A is simpler and already patterns the existing hold-to-trigger button. **Life-safety surface** — a blind admin MUST be able to confirm what severity they selected before the 3-second hold.

### A-03 — P2: Template gallery preview modal lacks return-focus-on-close

**Severity: P2**

The template preview modal (`TemplatePreviewModal` component, `templates/page.tsx:1344-1410`) adds an Escape handler:
```ts
const onKey = (e: KeyboardEvent) => { if (e.key === 'Escape') onClose(); };
```
But there is **no `useRef` storing the trigger element** and no `ref.current.focus()` call after close. When a keyboard user opens a preview and dismisses it, focus falls to the `<body>` or is lost entirely, violating WCAG 2.4.3 Focus Order.

**Evidence:** `apps/web/src/app/[schoolId]/templates/page.tsx:1344-1350` — `useEffect` registers Escape handler but stores no `previouslyFocusedElement` ref.

**Fix:** Before opening:
```tsx
const triggerRef = useRef<HTMLElement | null>(null);
// on open:
triggerRef.current = document.activeElement as HTMLElement;
// on close:
triggerRef.current?.focus();
```
Standard pattern for dialogs. Note: the templates page already has `/* eslint-disable jsx-a11y/click-events-have-key-events, jsx-a11y/no-static-element-interactions */` at line 4, which is suppressing some related warnings.

### A-04 — P2: `eslint-disable jsx-a11y` file-level suppression on templates/page.tsx hides real violations

**Severity: P2**

`apps/web/src/app/[schoolId]/templates/page.tsx:4` disables **three** jsx-a11y rules wholesale for the entire 2,400-line file:

**Evidence:** `apps/web/src/app/[schoolId]/templates/page.tsx:1-5` (file header).

**Fix:** Convert suppression to targeted `// eslint-disable-next-line` on the specific lines that genuinely need it (e.g., drag-drop handlers on list items), rather than suppressing globally. Re-audit the file for any unlabelled inputs exposed since 2026-04-16.

### A-05 — P3: Branding injection has no WCAG AA contrast enforcement at ink derivation time

**Severity: P3**

The `cssVarsFromPalette()` function in `apps/web/src/lib/branding.ts` passes `primaryInk` and `accentInk` through verbatim from the `TenantBranding.palette` DB record:
```ts
safe('--brand-primary-ink', p.primaryInk);
safe('--brand-accent-ink', p.accentInk);
```
If a tenant adopts a light primary color (e.g. `#f0f0f0`) and the scraper defaults `primaryInk` to `#ffffff` (the default for most brands), the injected CSS will render **white text on near-white background** across the entire admin dashboard chrome. There is NO contrast check at injection time — neither in `applyBranding()` nor in `cssVarsFromPalette()`.

**Evidence:**
- `apps/web/src/lib/branding.ts:87,91` — raw passthrough.
- `apps/web/src/lib/branding.ts:158` — default `primaryInk: '#ffffff'` and `accentInk: '#ffffff'`.
- `apps/web/src/components/branding/BrandingWizard.tsx:1048-1050` — WCAG contrast IS checked in the wizard preview UI (contrast ratio + grade shown), but this check is in the **wizard display only** and does not block saving or injecting a failing palette.

**Context:** The branding scraper auto-adopts palette from the tenant's website. If it scrapes a light primary color and defaults ink to white, the admin CMS shell becomes inaccessible without the operator noticing until they log out/in or refresh.

**Fix — two options:**
1. In `cssVarsFromPalette()`, derive `primaryInk` dynamically: if the luminance of `primary` > 0.18 (roughly #aaa), set `primaryInk = '#0f172a'`; else `#ffffff`. This matches the branding wizard's "AA" logic.
2. At minimum, add the same contrast-fail warning shown in the wizard to the branding settings "Current brand" display so operators can see when their auto-adopted palette fails AA.

**Note:** The BrandingWizard DOES show a live contrast checker and warns on fail — the gap is that it does not BLOCK adoption of a failing palette, and the raw injection path bypasses it entirely.

### A-06 — P3: No focus trap on several modal patterns (non-EmergencyOverlay)

**Severity: P3**

`EmergencyOverlay.tsx` has a manual focus trap (lines 44-61). The `PlaylistCreateWizard.tsx` uses `aria-modal="true"` but has no corresponding focus trap — Tab can escape the wizard into the background page. Similarly, `playlists/page.tsx:1899` and `screens/page.tsx:2245` both use `role="dialog" aria-modal="true"` with no programmatic focus containment.

`aria-modal="true"` **does not** implement a focus trap in browsers that don't support it natively (which is most of them for custom dialogs). The spec relies on browsers to implement this, but support is incomplete, especially on Safari.

**Evidence:**
- `apps/web/src/components/playlists/PlaylistCreateWizard.tsx:975` — `aria-modal="true"` with no trap.
- `apps/web/src/app/[schoolId]/screens/page.tsx:2245` — `aria-modal="true"` with no trap.
- `apps/web/src/components/layout/EmergencyOverlay.tsx:44-61` — only emergency overlay has real trap.

**Fix:** Extract the focus trap from `EmergencyOverlay` into a reusable `useFocusTrap(containerRef)` hook and apply it to the wizard and pair-screen modal. The emergency overlay pattern is already proven — just share it.

### A-07 — P3: Broadcast page textarea and media URL inputs lack `id`/`htmlFor` pairs

**Severity: P3**

The broadcast page composer uses `<label className="block text-xs ...">Message</label>` (line 249) and `<textarea .../>` (line 250) as siblings with **no `htmlFor`/`id` pair**. Screen readers will not associate the label with the textarea. Same pattern for Duration input (line 306-313) and audio URL (line 295-300).

**Evidence:** `apps/web/src/app/[schoolId]/emergency/broadcast/page.tsx:249-257` — label and textarea are siblings, no `id` on textarea, no `htmlFor` on label.

**Fix:**
```tsx
<label htmlFor="broadcast-message" ...>Message</label>
<textarea id="broadcast-message" .../>
```
Life-safety surface — this should be P2 except the aria-label on the hold button covers the primary action.

## Overall Assessment

### Design: A−
The emergency surfaces look appropriately high-contrast (dark theme, orange/red hierarchy). The fleet map legend is clean and readable. The branding system can visually degrade if a light-primary tenant adopts without manually fixing ink colors — that is the one design gap with a11y implications.

### UX: B+
Keyboard operators can complete all flows: login (Tab/Enter), template gallery (Tab to cards, Enter to open, Escape to close), screens (Enter/Escape on modals), playlist wizard (Tab/Escape, aria-labels on assets). The broadcast console keyboard hold-to-trigger is explicitly implemented with Space/Enter + keydown/keyup lifecycle. The gap is return-focus-on-close for the template preview modal, and the severity buttons not announcing their selected state to SR users.

### Functionality: B+
The axe CI gate is real and blocking (baseline=1, fires on push). Emergency surfaces have correct aria-live with Web Speech API bonus. Fleet map is color-blind safe with shape+color+label. The authenticated-route coverage gap means axe is only verifying login shells, not real operator workflows — a meaningful gap that CI cannot currently catch. No critical a11y violations found in code reading, but the unaudited authed surfaces leave real risk.

## Legal Context Note

VenueOS sells to K-12 school districts. Under ADA Title II (2024 DOJ rule, effective April 2026 for larger districts) and Section 504, school districts operating web-based software used by their employees are responsible for ensuring it meets WCAG 2.1 AA. The school district, as the customer, will be liable — but VenueOS will face churn and reputation risk when districts do compliance audits. The current state (B+ functionality) is acceptable for a launch with a single pilot district. It must be brought to A before enterprise rollout.

The emergency broadcast console has special weight: a blind superintendent who cannot tab to the severity selector and confirm it without visual confirmation is a real accessibility gap on a life-safety surface. A-02 should be P1 for that reason alone.
