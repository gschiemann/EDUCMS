#### 1. Tenant-wide emergency loses the incident TYPE — screens render the SEVERITY ("CRITICAL PROTOCOL ACTIVE") instead of LOCKDOWN / EVACUATE / SHELTER

**Where:** `apps/api/src/emergency/emergency.controller.ts:496 → apps/api/src/screens/screens.controller.ts:2795,2833`

#### 2. WS clock-skew compensation never engages (field-name mismatch) — every signed emergency push is dropped on a kiosk whose clock is >30s off

**Where:** `apps/web/src/app/player/page.tsx:4291 vs apps/api/src/realtime/realtime.gateway.ts:324-329`

**Failure:** The gateway ships `serverTime` on AUTH_OK specifically so the player can correct for Android signage boxes that boot without NTP (the comment at realtime.gateway.ts:196-203 says so verbatim). But the outbound frame puts the body under the key `payload`, while the player reads `msg?.data?.serverTime` — a key the gateway never emits. `serverClockOffsetRef.current` is therefore permanently 0, and the 'Large clock skew detected' warning can never fire. The freshness gate at page.tsx:4346 then compares the raw device clock: `Math.abs(Date.now() + 0 - msg.timestamp) > 30_000`. On any kiosk drifting more than 30s, EVERY SENSITIVE_TYPES message — OVERRIDE, SOS, TEXT_BROADCAST, MEDIA_ALERT, ALL_CLEAR_MESSAGE — is silently dropped with 'dropped stale/future event'. Real-time delivery on that unit is dead; the alert only lands via the 10s manifest poll (OVERRIDE) or the EmergencyOverlay's 10s /emergency/messages poll (SOS/broadcast), and the all-clear for a pushed message only clears via the 12s reconcile. This is exactly the failure the code was written to prevent, on exactly the hardware class in production (Android WebView / Taurus kiosks), and it is invisible — there is no server-side signal that a screen is dropping pushes.

### Should-fix

- Redis never reconnects after a blip, and publish() then reaches nobody. redis.service.ts:95-101 `retryStrategy` returns null after 3 attempts (ioredis stops retrying permanently) and `reconnectOnError: () => false`; `this.connected` (line 44) is set true at boot and is only ever set false inside the onModuleInit catch (line 149) — never on 'end'/'close'. After a >~2.4s Redis outage the process is permanently Redis-less but still believes it is connected, so publish() (line 210) takes the `connected` branch, `publisher.publish()` rejects (enableOfflineQueue:false), and the `else` branch that pipes straight to the in-process WS gateway + SSE is SKIPPED. Result: an emergency trigger reaches zero WS/SSE clients — even ones connected to this very replica — and every alert falls back to the 10s manifest poll until the API is redeployed. Fix: reset `connected=false` on the client's 'end' event, add a bounded infinite retryStrategy, and catch inside publish() so it falls through to the local gateway.

- Global 600 req/min per-IP throttle is not exempted on the emergency/manifest path, and the emergency cadence makes it worse. app.module.ts:190 sets `throttlers: [{ ttl: 60000, limit: 600 }]` and ClientIpThrottlerGuard keys on the leftmost X-Forwarded-For, i.e. the building's single NAT public IP (screens.controller.ts:180-187 already documents 'school NAT means all ~10-30 existing kiosks + dashboard users share ONE public IP'). Each playing kiosk makes ~15.5 API calls/min at rest (manifest emergencyPoll 10s = 6, reconcile 30s = 2, cache-status 30s = 2, render-proof 30s = 2, heartbeat 30s = 2, pingStatus 45s = 1.3) and ~21.5/min once activeEmergency flips the poll to 5s (page.tsx:4658-4660). That is ~28-38 screens per public IP before the shared bucket 429s — and it bites hardest DURING an incident. `/screens/:id/manifest` carries no @SkipThrottle and no @Throttle of its own. Not hit today (largest live tenant is 9 screens) but it is the first wall a district-scale rollout meets.

- Tenant-scope emergencies do not cascade to child tenants. resolveScopeTenant (emergency.controller.ts:278) treats scopeId as the tenantId verbatim and rejects any tenant that is not the caller's own (line 312), and the manifest only ever reads the screen's OWN tenant row (screens.controller.ts:2572-2611) — nothing consults Tenant.parentId. Both trigger UIs post `scopeId: user.tenantId` (actions/trigger-emergency.ts:37, EmergencyTriggerModal.tsx, panic/page.tsx:307). So a DISTRICT_ADMIN sitting on a parent tenant who hits LOCKDOWN reaches only screens whose tenant_id is the parent row; every child location shows nothing, with no error and no UI affordance to target a child other than switching tenants first. The hierarchy is live in production (Chardon High School is the parent of Chardon Middle School and Fremont Elementary; Springfield School District is the parent of Springfield Elementary, which owns 3 screens).

- The SSE tier has no freshness gate, no signature presence check, and no per-eventId dedup — page.tsx:4127-4141 comments 'SSE doesn't have the signed-replay protection the WS path uses'. Defensible because the fan-out is HMAC-verified server-side (redis.service.ts:191) and the stream is device-JWT-authed, but it means the WS and SSE tiers enforce materially different client-side guarantees for the same signed life-safety messages. Worth making explicit (or symmetric) before an external security review.

- Severity enums diverge between the two trigger surfaces writing the same column. packages/api-types/src/index.ts:130 `Severity = ['LOW','MODERATE','HIGH','CRITICAL']` (tenant/group/device trigger) vs screen-emergency.controller.ts:83 `ALLOWED_SEVERITIES = ['LOW','MEDIUM','HIGH','CRITICAL']` (per-screen trigger). Both feed ScreenEmergencyOverride.severity and the manifest's fallback-colour switch at screens.controller.ts:2834-2838, which handles neither MODERATE nor MEDIUM explicitly (both fall to the amber default). Pick one vocabulary.

- The WS gateway captures group identity once at HELLO (realtime.gateway.ts:171 `decoded.groupId = screen.screenGroupId`) and never refreshes it, and broadcastToScope matches on that cached value (line 271). A screen moved between screen groups keeps its stale ctx.groupId for the life of the socket, so a group-scoped lockdown on its NEW group never reaches it in real time — it only lands via the manifest poll (the per-screen ScreenEmergencyOverride row written by the group trigger does cover it, so nothing is lost, just delayed). Same staleness exists for an already-open socket whose Screen row is deleted: processHello rejects at connect, but there is no periodic re-check the way SseService.tickRevocation does at 30s.

- The tenant-scope trigger builds ONE Prisma batch $transaction containing the tenant update + audit row + one screenEmergencyOverride.upsert per screen (emergency.controller.ts:457-521), preceded by an unselected `screen.findMany({ where: { tenantId } })` that pulls every emergency column of every row. Unbounded by screen count — the bulk per-screen endpoint caps at 500 (screen-emergency.controller.ts:528) but this path has no cap. At district scale this is the longest-held transaction in the app, on the life-safety write path, against a pgBouncer pool of 10.

- GET /api/v1/emergency/status (emergency.controller.ts:1192) carries no @RequireRoles, so a RESTRICTED_VIEWER can read their tenant's live emergency state and every active SOS/broadcast message body. Probably intended (read-only, own tenant only, and the player's browser-preview path uses it), but it is the one emergency route with no explicit role list — worth an explicit decorator so the intent is legible rather than inherited from RbacGuard's 'no roles ⇒ allow'.

- In the Redis-down fallback, RedisService.publish() routes EVERY channel through handleRedisMessage — including the unsigned `metrics:ack` publish from the WS gateway (realtime.gateway.ts:246). verifyWsHmac fails on it and logs `[WS] DROPPED unverified message on metrics:ack` at warn level for every ACK from every screen, which will bury the genuine forged-message warnings this log line exists to surface.

#### 2. Same tenant-less device JWT reads ANY tenant's template or published asset via the /playback endpoints (null-scope fallthrough)

**Where:** `apps/api/src/templates/templates.controller.ts:780`

**Failure:** Both /playback endpoints branch on `u.kind === 'device'` and set scopeTenantId = screen.tenantId ?? null. For the unclaimed screen minted above, screen.tenantId is NULL, so scopeTenantId becomes null — the same value that means "SUPER_ADMIN, cross-tenant by design". The template query then falls into `OR: [{isSystem:true},{tenantId:{not:null}}]`, which matches EVERY template in EVERY tenant, and the asset query spreads NOTHING for the tenant filter, matching any PUBLISHED asset in any tenant and returning its fileUrl. A competitor or attacker holding a customer's template/asset id (they appear in dashboard URLs, shared links, support tickets, and player traffic) reads that customer's board copy, zone config, menu pricing and asset URLs with a credential obtained anonymously in one unauthenticated POST. **Failure:** An operator pastes a normal multi-parameter URL into a WEBPAGE widget (Google Sheets published view `?gid=0&single=true&widget=false`, a BI dashboard, a ticketing board, a YouTube watch link) or an RSS/ICS feed URL. The server rewrites `&` to `&amp;` before fetching, so the upstream receives garbage parameter names (`amp;single`) and returns the wrong page / an error. The screen shows a broken board and nothing in the UI explains why. Same corruption applies to every saved text field: a tenant/screen/playlist/menu-item named "Bar & Grill" is persisted as "Bar &amp; Grill" and renders literally, and each re-save compounds it (`&amp;amp;`).

<details><summary>Evidence</summary>

LIVE against production (commit c5041a09 == HEAD): `curl 'https://api-production-39a1.up.railway.app/api/v1/proxy/web?url=https%3A%2F%2Fhttpbin.org%2Fget%3Fa%3D1%26b%3D2'` returned httpbin's echo `"args": { "a": "1", "amp;b": "2" }` — the second param name was corrupted. Mechanism confirmed by three independent methods: (1) running the exact pipe options in node — `sanitizeHtml('https://x/?a=1&b=2')` → `https://x/?a=1&amp;b=2`; (2) @nestjs/core `router-execution-context.js:124-131` `isPipeable()` includes BODY, QUERY and PARAM, so the global pipe runs on every `@Query('url')` (proxy.controller.ts:40, feeds.controller.ts:57/69, youtube-live.controller.ts:61) and every `@Body()`; (3) the repo's own code already documents the body half — templates.controller.ts:96-101 ("the global SanitizationPipe (APP_PIPE) runs sanitize-html on EVERY request-body string") and the regression test ai/designer-prompt.spec.ts:172-192 ("RAW html is destroyed by the pipe (the original bug)").

</details>

#### 2. POST /screens/:id/render-proof is capped at 10/min per CLIENT IP but every screen posts 2/min — a site with ≥6 screens behind one NAT IP gets 429'd and its screens falsely report FROZEN

**Where:** `apps/api/src/screens/screens.controller.ts:3374`

**Failure:** All screens at a customer site egress from one public IP, and the throttle key is that IP (leftmost X-Forwarded-For). A 6+ screen school/venue generates ≥12 render-proof POSTs/min against a 10/min bucket; once tripped the throttler blocks for the full 60s window, so most posts are dropped every minute. `lastRenderedAt` then exceeds the 90s RENDER_PROOF_STALE_MS window (apps/api/src/screens/render-proof.ts:38) and screens that are painting perfectly are reported `renderHealth: STALE` / `renderStale: true`. On the Sports game console that renders as a red pill reading "FROZEN — reachable but no frame painted in Xs" (apps/web/src/app/[schoolId]/sports/[gameId]/SurfaceHealthPills.tsx:135-164) mid-game.

### Should-fix

- Systemic: every per-route @Throttle in the app is keyed on the client's public IP, so the limit is per-SITE, not per-device. Re-key device endpoints on the screenId/device-JWT sub (or raise them by expected fleet size). Beyond the two blockers above, the same math threatens: `/screens/status/:fp/crash-report` 10/min (screens.controller.ts:858), `/screens/unpair/:fp` 5/min (:1294), `/screens/:id/gpio-event` 30/min (gpio.controller.ts:133 — a school with wired panic buttons shares one bucket), `/proxy/web` 60/min (proxy.controller.ts:38 — comment assumes "a single screen doesn't iframe-refresh more than once a minute", but the cap is site-wide), `/feeds/rss` and `/feeds/ics` 60/min each (feeds.controller.ts:56,68).

- GET /api/v1/screens/status/:deviceFingerprint is unauthenticated and returns `pairingCode` plus name/version/OTA state, and writes lastPingAt/status on every call (screens.controller.ts:546, response at :713-717). Anyone who learns a fingerprint can read the pairing code and keep a dead screen showing ONLINE. Gate it on the device JWT (the player already holds one) or drop pairingCode once tenantId is set.

- GET /api/v1/fitness/youtube-live/resolve is unauthenticated with NO @Throttle at all (youtube-live.controller.ts:60) — an anonymous caller can drive unbounded outbound scrapes through the production server IP. It relies solely on the global 600/min-per-handler-per-IP default. (Previously flagged as P3-2 in docs/research/2026-06-08-launch-readiness-audit/03-security-authz.md and still unfixed.)

- A DEVICE JWT satisfies JwtAuthGuard and then passes RbacGuard unconditionally on any route that declares no @RequireRoles (rbac.guard.ts:27 `if (!requiredRoles) return true`). 13 guarded mutations currently have no role gate — including POST /tenants/switch (tenants.controller.ts:191), PUT /users/me (users.controller.ts:154), POST /tenants/me/usb-ingest/screens/:screenId/event (:1016) and the MFA enroll/verify/disable/backup-codes routes (mfa.controller.ts:155,233,328,379). Blast radius is small today (a device payload has no role and id=screenId), but the default should be deny, not allow.

- apps/api/src/realtime/sse.controller.ts:56 calls `requireSecret('DEVICE_JWT_SECRET')` with no `devFallback`, so it resolves to the empty string in dev/test while every other call site uses `dev_only_device_jwt_secret_CHANGE_ME` (screens.controller.ts:91, gpio.controller.ts:82, jwt-auth.guard.ts:78). Dev-only, but it makes SSE auth silently unverifiable locally.

- `process.on('uncaughtException')` logs and lets the process continue in a possibly-corrupted state (main.ts:28-31). Deliberate per the comment, but combined with `restartPolicyMaxRetries: 10` a crash-and-restart would be safer than serving from a poisoned event loop.

- apps/api/src/health/health.controller.ts:28-35 `withTimeout` never clears its setTimeout, so every liveness probe (Railway hits it every few seconds) leaves a pending timer for 200-1500ms. Harmless at current volume; clear the timer in a finally.
