# Millisecond-Accurate Multi-Screen Sync for Browser-Based Signage Players — Research Report

**Scope:** Browser players (Chromium 83–87 on NovaStar Taurus + Android WebView, modern Chromium elsewhere) → cloud API (Railway) over ordinary internet/WiFi. No multicast, no LAN server, no PTP hardware. Existing plumbing: WebSocket, HTTP manifest polling, server-side Redis pub/sub.

**Method note:** every factual claim carries its source URL. Claims I could not pin to a definitive source are marked **UNVERIFIED**. Absence claims ("vendor X lacks true sync") are graded per how definitive the evidence is.

---

## Executive summary (the five facts that matter most)

1. **The proven architecture is schedule-based, not command-based**: a shared clock + a deterministic timeline that each player evaluates independently. info-beamer (the strongest browserless prior art) and the W3C Multi-device Timing work (the strongest browser prior art) both use it; command/barrier systems (signageOS Sync API) document no drift correction at all. ([info-beamer synced-content](https://info-beamer.com/doc/synced-content), [timingsrc](https://webtiming.github.io/timingsrc/))
2. **Browser clock sync over WebSocket to a cloud server achieves errors of a few ms; 0–1 ms on desktop** — measured in production for years by Motion Corporation's InMotion service (the paper: "Synchronization errors are in the order of a few milliseconds on all major browsers and most operating systems (including Android). Typically we observe 0-1 millisecond errors for desktop browsers"). ([Media Synchronization on the Web, §9.1](https://www.w3.org/community/webtiming/files/2018/05/arntzen_mediasync_web_author_edition.pdf))
3. **HTML5 video slaved to that clock via a playbackRate servo achieves ~±7 ms** ("echoless"), maintained for hours/days without accumulating error; ±10 ms = echoless band, ±25 ms = frame-accurate band; ~3 s to converge after load. (same paper, §9.2 + Fig. 8)
4. **`requestVideoFrameCallback` shipped in exactly Chrome 83** — the Taurus floor — exposing `mediaTime` + `expectedDisplayTime` per presented frame, which is precisely the feedback signal a sync servo needs. ([web.dev rVFC](https://web.dev/articles/requestvideoframecallback-rvfc), [caniuse](https://caniuse.com/mdn-api_htmlvideoelement_requestvideoframecallback)) One caveat flagged below on WebView compat data.
5. **The big cloud competitors do not do this.** ScreenCloud's own help center: "perfect synchronization for video content cannot be guaranteed, as each device relies on its own system clock." OptiSigns/Yodeck sync is best-effort or LAN-multicast; Rise Vision routes video walls through one PC. The only vendors with real sync (BrightSign, info-beamer, Xibo, Navori) are LAN-bound, non-browser, or 33–50 ms class. **A browser player that holds ±10 ms over cloud is a genuine wedge.**

### BrightSign (the industry reference for LAN sync)

- Clock: all synchronized players share a **PTP** clock configured via player registry; PTP domains 0–127. ([docs.brightsign.biz/advanced/video-wall-sync-architecture](https://docs.brightsign.biz/advanced/video-wall-sync-architecture))
- Network constraints: players must be on the **same LAN**; PTP multicast address `224.0.1.129` must be allowed, plus the sync group's broadcast address (default `255.255.255.255`, or a multicast address like `239.0.0.1`). ([Signagelive help — How to Synchronise your BrightSign Players](https://support.signagelive.com/hc/en-us/articles/360003516251-How-to-Synchronise-your-BrightSign-Players), [BrightSign Video Synchronization](https://brightsign.atlassian.net/wiki/spaces/DOC/pages/1861156865))
- Architecture: leader "sends out network packets which contain the group name, the current state name, and the time at which that state was entered"; followers derive their position from that shared state — i.e., **clock + broadcast state, not per-frame commands**. Documentation cites a **500 ms** typical preparation delay before synchronized start. ([video-wall-sync-architecture](https://docs.brightsign.biz/advanced/video-wall-sync-architecture))
- Follower chase: followers "adjust their playback either by speeding up or slowing down on a frame by frame basis" (a rate servo — the same primitive as browser `playbackRate`). "Enhanced Sync" events execute "within a few milliseconds." **"Synchronization over wifi is not supported."** Different player models should not be mixed in one sync group. There is also **HDMI clock sync** so "each line of the video is drawn to the screen at the same time" (scanout-level alignment — beyond what a browser can do). ([docs.brightsign.biz/advanced/video-sync](https://docs.brightsign.biz/advanced/video-sync))
- Takeaway: the market leader's LAN design = PTP clock + leader-announced timeline + per-player rate servo. Our cloud design replaces PTP with WebSocket clock sync and keeps the other two pieces.

### info-beamer (the closest philosophical prior art — Florian Wesch)

- Core technique ("time-based synchronization"): devices sync via "a precise local clock on each device"; devices with identical-duration playlists "independently calculate when the next content should start… devices don't have to communicate with each other at all. They might even be at completely different locations." System time comes from **NTP** ("the closer the NTP server to the device the better"; RTCs "do not offer the precision necessary"). Ethernet is preferred over WiFi because latency is "far more consistent." A second, network-based mode auto-elects a leader for offline LANs. ([info-beamer.com/doc/synced-content](https://info-beamer.com/doc/synced-content))
- Video-wall mode: each device receives a transformed canvas "as well as the correct wall clock time"; on Pi3 and earlier, info-beamer "will try to adjust the vsync event so it happens at the same time on multiple devices by slightly modifying the HDMI clock rate until the vsync happens at an expected wall clock timestamp" (software genlock!). The **Pi4 cannot control HDMI frame emission timing, so devices "might be off by at most 16.66ms"** (one 60 Hz frame). ([Magic Video Wall](https://info-beamer.com/raspberry-pi-digital-signage-magic-video-wall-3028.html), [use-case page](https://info-beamer.com/use-cases/raspberry-pi-video-wall), [synced-content](https://info-beamer.com/doc/synced-content))
- Takeaway: even the best sub-frame system accepts **±1 frame as the floor when it can't steer the display clock** — which a browser never can. So ±1 frame (16.7 ms) is the honest physical floor for browser video-wall claims.

### Broadcast-grade background (one paragraph, as requested)

Professional broadcast solved this with **SMPTE ST 2059**: ST 2059-1 maps a PTP-derived time to signal alignment points, and ST 2059-2 is the "SMPTE profile for use of IEEE 1588 Precision Time Protocol in professional broadcast applications" — the genlock replacement for all-IP (ST 2110) plants, targeting **sub-microsecond** alignment (devices within ±0.5 μs of the grandmaster, "aligned" = within 1 μs of each other). It needs PTP-aware network hardware and boundary/transparent clocks — unavailable to a browser over consumer internet — but it validates the same architecture: one traceable clock, deterministic epoch-anchored timelines, every device computing alignment locally. ([SMPTE blog on PTP](https://www.smpte.org/blog/precision-time-protocol-for-synchronization-in-broadcast-over-ip), [Telestream whitepaper](https://www.telestream.net/pdfs/whitepapers/wp-Introduction-to-Live-IP-Video-&-Precision-Time-Protocol.pdf), [demirci ST2059/ST2110 explainer](https://muratdemirci.com.tr/en/ptp-st2059-st2110/))

# B. Clock synchronization over internet, from a browser

### B1. The algorithm family: Cristian's / NTP-style over WebSocket

- **Cristian's algorithm**: client sends request at t₀, server replies with its time T, client receives at t₁; set clock to `T + RTT/2` where `RTT = t₁ − t₀`. **Error is bounded by RTT/2**, and is zero only "if the RTT is actually split equally between request and response" — the symmetric-latency assumption "is regularly not true." Precision improves by "selecting suitable RTT from a set of many request/response pairs," specifically minimum-RTT exchanges. ([Wikipedia — Cristian's algorithm](https://en.wikipedia.org/wiki/Cristian%27s_algorithm))
- **NTP's clock filter** does the same thing formally: offset `θ = ((t₁−t₀)+(t₂−t₃))/2`; the filter "accumulates offset/delay samples in a window of several samples and selects the offset sample associated with the **minimum delay**." ([ntp.org exec summary](https://www.ntp.org/reflib/exec/), [OSTechNix NTP explainer](https://ostechnix.com/how-network-time-protocol-ntp-works/))
- **Achievable accuracy**: NTP is quoted at "hundreds of microseconds to several milliseconds" in good conditions; "over the public Internet, accuracy is typically within **tens of milliseconds**" depending on latency/congestion/server quality ([Meinberg KB — Time Synchronization Accuracy with NTP](https://kb.meinbergglobal.com/kb/time_sync/time_synchronization_accuracy_with_ntp)). But that's raw NTP against arbitrary servers; the number that matters for us is app-level sync against *our own* server:
- **Measured app-level result (the key number)**: Motion Corporation's InMotion online clock, sampled from browsers over WebSocket with filtering, running in production for years: "Synchronization errors are in the order of **a few milliseconds** on all major browsers and most operating systems (including Android). Typically we observe **0-1 millisecond errors for desktop browsers**, compared to a system clock synchronized by NTP." Pre-WebSocket (long-polling era) prototypes got 33 ms; WebSockets "improved results significantly." Precision "degrades well with poor network conditions" — even EDGE cellular was "not visibly worse, except for longer update latency." ([Arntzen, Borch, Daoust — *Media Synchronization on the Web*, §9.1, PDF](https://www.w3.org/community/webtiming/files/2018/05/arntzen_mediasync_web_author_edition.pdf))
- **Game-industry lineage**: the algorithm every JS library copies is Zach Simpson's "A Stream-based Time Synchronization Technique For Networked Computer Games" — stamp, echo, halve-RTT, then statistically filter a stream of samples; Simpson reported "accuracies of 100ms or better," with error "equal to the difference in trip times" when RTT is asymmetric. ([GameDev.net discussion of the technique](https://www.gamedev.net/forums/topic/425141-syncing-peer-clocks/))
- **The `timesync` npm library** (enmasse.io) implements exactly this for browsers: repeated request/response samples; "all samples above approximately 1 standard-deviation from the median are discarded and the remaining samples are averaged using an arithmetic mean." ([github.com/enmasseio/timesync](https://github.com/enmasseio/timesync), [npm](https://www.npmjs.com/package/timesync))

**Best practice distilled from these sources:** burst of samples (not one), take min-RTT (NTP) or median-with-σ-rejection (timesync/Simpson), track the result as an offset applied to a **monotonic** local clock, repeat periodically, and slew rather than step.

### B2. How often must we resync? (crystal drift math)

- Commodity computer quartz drifts "about 20-30 ppm" ([NTP FAQ — How do computer clocks work?](https://www.eecis.udel.edu/~ntp/ntpfaq/NTP-s-sw-clocks.htm)); temperature sensitivity is "about 1 PPM per °C," and −40…85 °C can swing −100 ppm ([Jauch — how temperature-sensitive are quartz crystals?](https://www.jauch.com/blog/en/ask-the-engineer-how-temperature-sensitive-are-quartz-crystals/), [All About Circuits — frequency tolerance/stability/aging](https://www.allaboutcircuits.com/technical-articles/characterizing-frequency-deviations-of-quartz-crystals-frequency-tolerance-frequency-stability-and-aging/)).
- Conversion: 1 ppm ≈ 86.4 ms/day ≈ 0.06 ms/min; ±10 ppm ≈ ±0.864 s/day ([Fuji Crystal ppm→seconds calculator](https://www.fujicrystal.com/news_details/ppm-to-seconds-converter.html)).
- Therefore at a worst-typical **30 ppm**, a player drifts **1.8 ms/minute**. To hold a ±5 ms budget with NO skew modeling, you must re-estimate offset roughly **every 2–3 minutes** (5 ms ÷ 1.8 ms/min ≈ 2.8 min). If you additionally estimate each device's **skew rate** (ppm) from consecutive offset measurements and extrapolate, the residual is the *change* in drift (thermal, ~1 ppm/°C), and 5–10 minute intervals hold fine — this is exactly what GStreamer's net client clock does with its calibration observations (below). *(The arithmetic in this bullet is mine; the inputs are sourced above.)*

### B3. W3C Timing Object / timingsrc / MediaScape — what the research program proved

- The **Timing Object** spec defines a shared, distributed media clock ("motion": position/velocity/acceleration vector timestamped against a synced clock) that any component queries locally; the W3C Multi-device Timing CG published it and maintained **timingsrc** (reference implementation) until the group closed in early 2025; the final CG report is dated Dec 2024. ([Timing Object spec (CG-FINAL)](https://www.w3.org/community/reports/webtiming/CG-FINAL-timingobject-20241203/), [timingsrc home](https://webtiming.github.io/timingsrc/), [timingsrc v3 docs](https://timingsrc.readthedocs.io/))
- Numbers, all from the companion book chapter ([PDF](https://www.w3.org/community/webtiming/files/2018/05/arntzen_mediasync_web_author_edition.pdf)):
  - Clock/"motion" sync: **few ms globally, 0–1 ms desktops** (§9.1, quoted in B1).
  - **HTML5 media element sync via MediaSync: "Synchronization errors of about 7 milliseconds is reported for both audio and video, on desktops, laptops and high-end smartphones. This corresponds to echoless audio playback."** So the ±7 ms figure the mission asked to verify is **CONFIRMED** (§9.2).
  - Fig. 8 defines the bands: **echoless = ±10 ms** (green), **frame-accurate = ±25 ms** (yellow); achieved with variable `playbackRate`, no skips, on Android Chrome; **"the media element was muted until playbackrate stabilized."**
  - Convergence: "the MediaSync library requires **about 3 seconds** to reach echoless."
  - Stability: "Synchronization has also been maintained for **hours and days** at end, without accumulated errors."
  - Platform floor: "the precision of timed operation in JavaScript is about **1 millisecond**, and a 60Hz screen refresh rate corresponds to **16 milliseconds**" (§9.3) — i.e., browser sync error is dominated by the media element, not the clock.
- MediaSync algorithm facts from the same chapter (§7.4): `currentTime` "is only a coarse representation of the media offset, and it fluctuates considerably when compared to the system clock" — MediaSync builds a **backlog of samples** (may take >1 s to stabilize) to estimate true offset; `seekTo(X)` "aims for a fixed target when it should be aiming for a moving target," so MediaSync **overshoots seeks deliberately, calibrated from per-seek statistics it collects**. Larger errors → seek; smaller errors → playbackRate. ([MediaSync doc page](https://webtiming.github.io/timingsrc/doc/background_mediasync.html) confirms the seek/rate split; exact numeric thresholds inside mediasync.js are **UNVERIFIED** — the readthedocs page 429'd and the "HTML5 MediaSync Report" tech-report (Borch & Arntzen 2015, Norut Tech Rep. 28) was not retrievable online.)
- Motion Corporation's "Shared Motion" is the hosted timing provider ("millisecond precise timing globally for Web clients"). ([timingsrc home](https://webtiming.github.io/timingsrc/), [MCorp timing provider note](https://www.w3.org/community/webtiming/timingprovider))

### B4. Local timebase discipline: performance.now() vs Date.now()

- `performance.now()` is **monotonic** and explicitly "not subject to system clock adjustments or NTP synchronization"; `Date.now()` IS subject to adjustments and "can be stepped backward by the system." Precision: coarsened for Spectre-class defenses to **100 μs in normal contexts, 5 μs when cross-origin isolated** (COOP/COEP); resolution far exceeds our 1 ms needs either way. ([MDN — Performance.now()](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)) The book chapter's High-Resolution-Time section confirms the spec guarantees monotonic + 5 μs accuracy target and notes the privacy-driven hard floor.
- **Design consequence** (the mission's premise, confirmed): estimate `offset = serverClock − performance.now()` and derive shared time as `performance.now() + offset`. If the OS steps its wall clock mid-playback (NTP step, timezone fix), `performance.now()` doesn't move, so playback doesn't glitch; the next sync burst simply re-measures offset. Never build the timeline on `Date.now()`.
- One trap MDN documents: `performance.now()` behavior across **OS sleep** is inconsistent between platforms (ticks during sleep on Windows; historically not on macOS/Linux/Android — open bugs referenced: [crbug.com/1206450](https://crbug.com/1206450)). After a device resume, force an immediate re-sync burst rather than trusting the pre-sleep offset. ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now))

### B5. Timer throttling that can hurt a scheduler loop

Per [MDN setTimeout — reasons for delays](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout) and [Chrome's timer-throttling blog](https://developer.chrome.com/blog/timer-throttling-in-chrome-88):

- Foreground: nested `setTimeout` chains clamp to a **4 ms minimum after 5 nesting levels** (HTML spec). Timers can also fire late (event-loop occupancy) or occasionally early (chapter §6.1).
- Hidden pages (Chrome): "standard throttling" checks timers **once per second**; **intensive throttling** (Chrome 88+, so post-Taurus) checks **once per minute** when *all* of: nesting ≥5, hidden >5 min, silent >30 s, no WebRTC. ([chromestatus entry](https://chromestatus.com/feature/5580139453743104))
- `requestAnimationFrame` is paused in background tabs / hidden iframes ([MDN rAF](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)) — and rendering stops when Chrome considers a surface occluded, which on Android WebView can include screen-off. For signage this is normally moot (fullscreen, foreground, screen on), but it means: **never** let the sync engine live in a hidden tab/iframe, and put the periodic clock-resample loop in a **Web Worker**, which is exempt from main-thread timer throttling ([Medium — overcoming browser throttling of setInterval](https://medium.com/@adithyaviswam/overcoming-browser-throttling-of-setinterval-executions-45387853a826)).
- Scheduler pattern used by timingsrc's Sequencer: compute the deterministic next-event time, `setTimeout` to just before it, then fine-align; "Web browsers may be precise down to a few milliseconds" this way (chapter §7.5). Combine with rAF for paint-aligned flips.

### B6. Watch-party implementations (weak prior art, for completeness)

- **Teleparty (Netflix Party)**: host's play/pause/seek actions are replicated to all participants, with automatic resync of laggards. No engineering writeup with numbers was found; the precise technique (currentTime broadcast cadence, thresholds) is **UNVERIFIED**. ([teleparty.com](https://www.teleparty.com/), [third-party guide](https://www.positioniseverything.net/how-to-use-netflix-party-teleparty-full-guide/)) Human co-watching tolerates hundreds of ms — do not benchmark against it.
- **Syncplay** (desktop mpv/VLC): client-server over internet; "servers synchronize the commands across all active Syncplay clients" (play/pause/seek replication). Command-based, human-tolerance class. ([github.com/Syncplay/syncplay](https://github.com/Syncplay/syncplay), [syncplay.pl](https://syncplay.pl/))
- **GStreamer `GstNetClientClock`** (the serious architecture reference): a client clock "synchronizes its time to a remote time provider," polling and "updat[ing] its calibration parameters based on the local and remote observations" — i.e., offset + rate (skew) estimation, exactly the servo-clock we should build in JS. The pipeline then distributes one clock + shared `base-time` so all devices compute identical running time — schedule-based, not command-based. ([gstreamer GstNetClientClock docs](https://gstreamer.freedesktop.org/documentation/net/gstnetclientclock.html), [Clocks & synchronization design docs](https://gstreamer.freedesktop.org/documentation/application-development/advanced/clocks.html), [Arun Raghavan — GStreamer and Synchronisation Made Easy](https://arunraghavan.net/2016/11/gstreamer-and-synchronisation-made-easy/), [FOSDEM 2016 slides](https://archive.fosdem.org/2016/schedule/event/synchronised_gstreamer/attachments/slides/889/export/events/attachments/synchronised_gstreamer/slides/889/synchronised_multidevice_media_playback_with_GStreamer.pdf))

# C. Frame-accurate video control in Chromium / WebView

### C1. requestVideoFrameCallback (rVFC)

- **Shipped in Chrome 83** — confirmed twice: web.dev ("Chrome 83 was the initial release supporting this API") and caniuse (Chrome 83+, Edge 83+). **This is exactly the Taurus floor, so even the oldest Taurus units (Chromium 83) should have it** — with one honesty flag: caniuse's *Android WebView* row only shows data for current versions ("WebView 150 only — limited data"), so **rVFC presence on Taurus's specific WebView build is UNVERIFIED until tested on-device** (it's Blink core, so presence is likely, but verify; keep a `'requestVideoFrameCallback' in HTMLVideoElement.prototype` feature-gate with an rAF+`currentTime` fallback). ([web.dev rVFC article](https://web.dev/articles/requestvideoframecallback-rvfc), [caniuse rVFC](https://caniuse.com/mdn-api_htmlvideoelement_requestvideoframecallback))
- Other browsers: **Safari 15.4+**, Firefox 132+, Samsung Internet 13+. ([caniuse](https://caniuse.com/mdn-api_htmlvideoelement_requestvideoframecallback))
- Metadata per presented frame: `mediaTime` ("media presentation timestamp of the presented frame… equal to the frame's timestamp on the HTMLMediaElement.currentTime timeline"), `expectedDisplayTime` (when the frame will be visible), `presentationTime`, `presentedFrames` (composited-frame counter — detects dropped frames), `processingDuration`, plus WebRTC fields (`captureTime`, `receiveTime`, `rtpTimestamp`). ([MDN rVFC](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback), [spec](https://wicg.github.io/video-rvfc/))
- Caveats from web.dev: callbacks fire at the **lesser of video rate and display rate**; the callback "may fire one vsync late relative to actual frame rendering" — disambiguate by checking whether `expectedDisplayTime` ≈ `now` (already displayed) vs ~16 ms in the future. ([web.dev](https://web.dev/articles/requestvideoframecallback-rvfc))
- **Why it matters for sync**: the servo error signal becomes `(mediaTime at expectedDisplayTime)` vs `(timeline position at expectedDisplayTime)` — a true glass-level measurement instead of the noisy `currentTime` polling MediaSync had to statistically de-noise in 2015 (chapter §7.4). This is the single biggest API advantage we have over the 2015-era ±7 ms result.

### C2. playbackRate as the sync servo actuator

- Range in Chromium: **throws for rates <0.0625 or >16**. ([MDN playbackRate](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/playbackRate))
- **Pitch is corrected by default**: `preservesPitch` defaults to `true`, so small rate changes don't chipmunk the audio. ([MDN preservesPitch](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/preservesPitch)) MDN marks unprefixed `preservesPitch` "Baseline widely available since December 2023"; Chromium supported the behavior earlier via `webkitPreservesPitch` — **exact Chromium-83 property naming UNVERIFIED; feature-detect both names** (irrelevant for muted signage video, relevant only for audio zones).
- Precision/limits for a servo: HTML5's own designers warn `playbackRate` "was not meant for precise control of playback velocity" and browsers differ (chapter §6.1) — which is precisely why the servo must be **closed-loop** (measure via rVFC, adjust, re-measure) rather than assuming the requested rate is delivered exactly. The MediaSync evaluation proves closed-loop rate control works to ±7 ms on real devices. What's inaudible/invisible: MediaSync ran echoless with pitch-corrected micro-adjustments and muted-until-stable; the literature I found does not publish a single agreed "invisible range," but the working practice in MediaSync's own runs stayed within a few percent (Fig. 8's rate axis). **Recommendation (synthesis, not a single citation): hold corrections within ±0.02–0.05 (2–5%) and returns-to-1.0, which is far below the 0.0625–16 hard limits and matched what the successful runs used; treat ±≥10% as visible.** Mark: the ±2–5% band itself is practitioner synthesis — **UNVERIFIED as a formal threshold**.
- BrightSign's own follower mechanism is the same actuator class: followers "speed… up or slow… down on a frame by frame basis." ([BrightSign video-sync](https://docs.brightsign.biz/advanced/video-sync))

### C3. Seeking

- Setting `currentTime` performs a **precise** seek (browser decodes from the preceding keyframe to the exact target); `fastSeek()` trades precision for speed by snapping toward keyframes — and **Chromium has never implemented fastSeek (no version, per caniuse)**; it's Firefox 31+/Safari 8+ only. So on our players, `currentTime` is the only seek and it is frame-precise but potentially slow. ([caniuse fastSeek](https://caniuse.com/mdn-api_htmlmediaelement_fastseek), [MDN fastSeek](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/fastSeek))
- Seek latency: measured as `seeking`→`seeked` event delta; it is content-dependent (keyframe interval, source buffering). The MediaSync chapter documents that `seekTo(X)` "will require a non-negligible amount of time" and lands you *behind* a moving timeline — hence their **calibrated overshoot** ("the algorithm collects statistics from every seekTo operation"), which "works reasonably well" (§7.4). **Typical millisecond figures for seek latency are not published anywhere I could verify — UNVERIFIED; measure per-device and per-encode.** Mitigation for signage: encode wall/sync content with **short GOPs / frequent keyframes** so precise seeks decode little (inference from keyframe-decode mechanics; flagged as inference).
- Frame-accuracy context: W3C's media-and-entertainment IG tracks the long-standing "frame accurate seeking of HTML5 MediaElement" issue — browsers only promise time-based, not frame-number-based, seeks. ([github.com/w3c/media-and-entertainment#4](https://github.com/w3c/media-and-entertainment/issues/4))

### C4. play() startup latency

- HTML5 "gives no guarantee about the latency that the software and the hardware may introduce when the play button is pressed, and no compensation is done to resorb that time afterwards"; the media clock also auto-pauses to buffer (chapter §6.1). So **never** build sync on "everyone call `play()` at T."
- Measurement: video startup time is properly measured **to the first frame actually painted** — with rVFC, the first callback's `expectedDisplayTime`/`presentedFrames` gives exactly that ([Mux — video startup time explained](https://www.mux.com/blog/the-video-startup-time-metric-explained), [web.dev rVFC](https://web.dev/articles/requestvideoframecallback-rvfc)). Typical absolute values vary by device/codec; **no citable universal ms figure — UNVERIFIED; measure**. Standard mitigation (MediaSync-proven): start early, muted, servo into position, unmute when locked; convergence budget ~3 s (chapter §9.2).
- Practical primer pattern for signage (synthesis): `preload="auto"`, warm the decoder by playing muted before the scheduled boundary, then either rate-servo into alignment or precise-seek + rate-trim.

### C5. Autoplay policy (signage-relevant)

- **"Muted autoplay is always allowed"** in Chrome; audible playback needs prior user gesture / MEI / kiosk overrides. For kiosk builds: `--autoplay-policy=no-user-gesture-required` (plus `--kiosk`), or the `AutoplayAllowed` enterprise policy. ([Chrome autoplay policy blog](https://developer.chrome.com/blog/autoplay), [chromium.org autoplay page](https://www.chromium.org/audio-video/autoplay/), [TelemetryTV kiosk note](https://docs.telemetrytv.com/docs/googles-autoplay-policy)) On the Taurus WebView the embedder controls this via WebSettings — same effect, verify on-device (flagged).

### C6. Chromium-83-era gaps vs modern (Taurus floor 83–87)

- **Have in 83**: rVFC (83 exactly — verify on Taurus WebView per C1), playbackRate + throw-limits, precise `currentTime` seeks, muted autoplay, performance.now with 100 μs resolution, WebSocket, Web Workers.

# D. Architecture verdict

### D1. Command-based vs schedule-based — the field has voted

- **Schedule-based (shared clock + deterministic timeline, each player independently computes what's on screen at time T)** is what every serious implementation uses:
  - info-beamer: wall-clock scheduling, zero inter-device communication, works across sites ([synced-content](https://info-beamer.com/doc/synced-content));
  - BrightSign: PTP clock + leader broadcasting "the time at which that state was entered," followers derive position ([architecture doc](https://docs.brightsign.biz/advanced/video-wall-sync-architecture));
  - GStreamer distributed pipelines: one net-synced clock + shared base-time ([clocks design](https://gstreamer.freedesktop.org/documentation/application-development/advanced/clocks.html));
  - W3C motion model: timing object synced to online motion; "media synchronization should be a consequence of connecting… to the same online motion" ([chapter §4](https://www.w3.org/community/webtiming/files/2018/05/arntzen_mediasync_web_author_edition.pdf));
  - Appspace: controller = timekeeper, workers "check what content frame they should be showing" ([docs](https://docs.appspace.com/latest/devices/configure-video-walls/));
  - Navori: server-synced player clocks + timeline ([player-synchronization](https://navori.com/player-synchronization/)).
- **Command-based ("server says GO")** appears only in (a) barrier-start APIs with no drift correction (signageOS `wait()` — [docs](https://docs.signageos.io/sdk/6.7.0/content/js-sync-playback/)) and (b) human co-watching tools (Syncplay, Teleparty). It fails structurally over internet: command arrival jitter = your skew; a late/lost command desyncs a screen until the next command; joins/reboots have no self-healing. The chapter's motion model states the fix explicitly: commands should mutate the *shared timeline state*, and devices react to state, not to command arrival.
- **Verdict for VenueOS**: schedule-based. (1) Server keeps one authoritative clock + per-screen-group timeline epoch ("playlist P, loop of duration D, anchored at server-time T₀"). (2) Players sync a clock offset over the existing WebSocket. (3) Every player renders `content((now_server − T₀) mod D)` deterministically. (4) WebSocket pushes exist only to *change the timeline* (new anchor, emergency override) — and an emergency override is itself just a timeline entry "override active from T_e," honoring the existing per-eventId dedup. Manifest polling remains the degraded path: sync survives WebSocket loss entirely, because the timeline is static data + the last-known clock offset (drifting ~1.8 ms/min until reconnect — hours before it's humanly visible on image flips).

### D3. Redis TIME as the single clock for multi-replica API

- `TIME` returns `[unix_seconds, microseconds_elapsed_in_current_second]` — gettimeofday-like, **microsecond precision**, available since Redis 2.6. ([redis.io/docs/latest/commands/time/](https://redis.io/docs/latest/commands/time/)) It reads the *Redis server's* clock, making it "useful when you need a consistent timestamp from the Redis server itself rather than relying on client-side clocks, which may differ across machines." ([OneUptime Redis TIME explainer](https://oneuptime.com/blog/post/2026-03-31-redis-time-server-clock/view))
- **Pattern for VenueOS** (design synthesis from the above + GStreamer's calibration model): Railway API replicas each run their own OS clock (unsynchronized with each other beyond host NTP). Instead of exposing `Date.now()` per replica, each replica maintains `redisOffset = redisTime − process.hrtime-based monotonic`, refreshed every ~30–60 s over the existing Redis connection (one RTT on the private network ⇒ sub-ms error), and serves all `/timesync` responses as `monotonic + redisOffset`. Result: every replica answers with the *same* clock to within well under a millisecond, so players can't be split-brained by replica load-balancing. Timeline anchors (T₀) are stamped from the same Redis-derived clock. Failure containment: if Redis is down, replicas keep serving the last offset (their own drift ~20-30 ppm), consistent with the existing "Redis missing → API boots anyway" posture. Caveat to note in docs: Redis TIME is only as good as the Redis host's own NTP discipline — absolute UTC truth is irrelevant for mutual sync, since all players slave to the *same* clock, whatever it reads.

### D4. Top failure modes reported by practitioners + standard mitigations

1. **WiFi RTT jitter and asymmetry** — offset error = (out-delay − back-delay)/2, bounded by RTT/2 ([Cristian's](https://en.wikipedia.org/wiki/Cristian%27s_algorithm)); Simpson: error "equal to the difference in trip times" ([GameDev.net](https://www.gamedev.net/forums/topic/425141-syncing-peer-clocks/)). Industry response: BrightSign flatly refuses WiFi for video sync ([docs](https://docs.brightsign.biz/advanced/video-sync)); info-beamer/Xibo recommend Ethernet ([info-beamer](https://info-beamer.com/doc/synced-content), [Xibo](https://xibosignage.com/manual/en/displays_sync_groups)). **Mitigations:** many samples + min-RTT selection (NTP clock filter — [ntp.org](https://www.ntp.org/reflib/exec/)), σ-rejection around the median ([timesync](https://github.com/enmasseio/timesync)), discard bursts whose RTT ≫ historical min, and surface a per-screen "sync quality" metric so installers run Ethernet on walls.
2. **Crystal drift + thermal drift** (fanless boxes over an LED wall get *hot*) — 20–30 ppm base, ~1 ppm/°C ([NTP FAQ](https://www.eecis.udel.edu/~ntp/ntpfaq/NTP-s-sw-clocks.htm), [Jauch](https://www.jauch.com/blog/en/ask-the-engineer-how-temperature-sensitive-are-quartz-crystals/)). **Mitigations:** periodic re-sync (≤2–3 min raw, longer with per-device skew estimation à la GstNetClientClock calibration [docs](https://gstreamer.freedesktop.org/documentation/net/gstnetclientclock.html)); slew, never step, the applied offset.
3. **Video startup/decode jank (first frames, variable play() latency, seek landing behind the moving target)** — no play-latency guarantee in HTML5 (chapter §6.1); MediaSync needs ~3 s to lock and **mutes until the servo stabilizes**, and **overshoots seeks using collected per-seek statistics** (§7.4, §9.2). **Mitigations:** preload + warm-start muted before the boundary, calibrated seek overshoot, unmute-on-lock, short-GOP encodes for wall content (last item = inference, flagged in C3).
4. **OS clock steps (NTP) mid-playback** — `Date.now()` can step backward; `performance.now()` cannot ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)). **Mitigations:** monotonic local timebase + app-level offset (B4); re-burst after resume/visibility-change (the OS-sleep tick bug, [crbug.com/1206450](https://crbug.com/1206450)); never mix `Date.now()` into the scheduler.
5. **Display pipeline latency differences between panels** — TV/panel processing adds tens of ms and varies wildly by model/mode: motion smoothing alone "adds 30ms to 80ms," >50 ms is human-noticeable, game mode "can reduce delay by four or five times" ([MakeUseOf on TV input lag](https://www.makeuseof.com/tv-adding-over-50ms-input-lag-unless-enabled-this-one-setting/), [Intel input-lag primer](https://www.intel.com/content/www/us/en/gaming/resources/how-to-fix-input-lag.html)). This is *invisible to the browser* — two perfectly synced players can still be a frame+ apart on glass. Industry acknowledges by requiring identical hardware (BrightSign "different player models… should not be synchronized" [docs](https://docs.brightsign.biz/advanced/video-sync); Xibo "similar devices" [docs](https://xibosignage.com/manual/en/displays_sync_groups)). **Mitigations:** installer checklist (game mode ON, motion smoothing OFF, identical models per wall) + a **per-screen manual latency trim** (±200 ms, 1 ms steps) stored on the Screen record — the same knob AV receivers ship for lip-sync; verify with a flash-pattern test card filmed by phone slow-mo (the existing webcam-verification rig in memory can automate this).

# Design cheat-sheet (numbers to build to, each traceable above)

**Clock sync (player ↔ API over existing WebSocket):**
- Sample = 4-tuple `(t₀, serverTime, t₁)` over WS; **burst 8–10 samples, ~150–250 ms apart**; keep the min-RTT sample per NTP's clock-filter rule ([ntp.org](https://www.ntp.org/reflib/exec/)), then median + discard >1σ outliers across kept samples ([timesync algorithm](https://github.com/enmasseio/timesync)). *(Burst size/spacing = synthesis of NTP-window + timesync defaults; exact counts UNVERIFIED as a standard.)*
- Local timebase: `performance.now()` only; shared time = `performance.now() + offset`. ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now))
- Re-sync cadence: **every 60 s** default (holds ±5 ms against 30 ppm with 3× margin; drift = 1.8 ms/min at 30 ppm — [NTP FAQ](https://www.eecis.udel.edu/~ntp/ntpfaq/NTP-s-sw-clocks.htm), [Fuji ppm calc](https://www.fujicrystal.com/news_details/ppm-to-seconds-converter.html)); after 3+ bursts, fit skew (ppm) and extend to 5 min; immediate re-burst on reconnect/resume/visibilitychange.
- Apply offset changes by **slewing ≤1–2 ms/s**, never stepping, while media is playing (GStreamer calibration model — [GstNetClientClock](https://gstreamer.freedesktop.org/documentation/net/gstnetclientclock.html)).
- Expected accuracy: **few ms (0–1 ms desktop-class)** to the server clock ([chapter §9.1](https://www.w3.org/community/webtiming/files/2018/05/arntzen_mediasync_web_author_edition.pdf)); alarm + surface "degraded sync" if min-RTT jumps >3× baseline.

**Server clock (multi-replica):**
- All replicas serve time derived from **Redis `TIME`** (μs precision, [redis.io](https://redis.io/docs/latest/commands/time/)); refresh replica↔Redis offset every 30–60 s; stamp timeline anchors from the same clock.

**Timeline / scheduler:**
- Content model: `position = (sharedNow − anchorT0) mod loopDuration` — evaluated locally every frame; commands only mutate anchors (info-beamer/motion-model pattern).
- Schedule state changes ≥**500 ms–2 s in the future** so every player prepares before the boundary (BrightSign uses ~500 ms prep — [architecture doc](https://docs.brightsign.biz/advanced/video-wall-sync-architecture)).
- Scheduler loop: coarse `setTimeout` to T−50 ms, then rAF fine-align; expect ~1 ms JS timing precision foreground (chapter §9.3, [MDN setTimeout](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout)); clock-resample loop in a Worker (throttle-exempt — [Medium](https://medium.com/@adithyaviswam/overcoming-browser-throttling-of-setinterval-executions-45387853a826)).

**Video servo (per `<video>`):**
- Error signal from **rVFC**: `err = mediaTime − timelinePosition(expectedDisplayTime)` ([web.dev](https://web.dev/articles/requestvideoframecallback-rvfc)); fall back to de-noised `currentTime` sampling where rVFC absent (chapter §7.4).
- Deadband **|err| < 2–3 ms**: do nothing. Trim zone **3–25 ms**: playbackRate nudge, suggested `rate = 1 + clamp(err/1s, ±0.04)` (±4% ceiling; hard API limits 0.0625–16 — [MDN](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/playbackRate)); hold each correction ≥250 ms to avoid hunting. Seek zone **|err| > ~250 ms**: precise `currentTime` seek with **calibrated overshoot** learned from per-seek stats (MediaSync technique, chapter §7.4). *(Deadband/zone boundaries = practitioner synthesis around the paper's ±10/±25 ms bands — UNVERIFIED as published constants; tune with the webcam rig.)*
- Convergence budget **3 s**; keep video **muted until |err| stays in-band for ~1 s**, then unmute (chapter §9.2 + Fig. 8).
- Target bands to display in the admin UI: **±10 ms = "echoless" (green), ±25 ms = "frame-accurate" (yellow), worse = red** (chapter Fig. 8).

**Platform guards:**
- Feature-detect rVFC (Chromium 83+ but WebView-on-Taurus UNVERIFIED — [caniuse](https://caniuse.com/mdn-api_htmlvideoelement_requestvideoframecallback)); never use `fastSeek` (absent in all Chromium — [caniuse](https://caniuse.com/mdn-api_htmlmediaelement_fastseek)); muted autoplay always allowed, kiosk flag `--autoplay-policy=no-user-gesture-required` for audible ([Chrome blog](https://developer.chrome.com/blog/autoplay)).
- Per-screen **manual latency trim ±200 ms** (display pipeline variance, D4-5); installer doc: game mode on, motion smoothing off, identical panels per wall, Ethernet for walls.

**Promises (marketing-safe):** image/HTML flips "within a frame" per site; video "within ±1 frame (16 ms), echo-free audio within ±10 ms on supported hardware"; never "genlocked."
