### [P0 · PROD] apps/web/src/hooks/use-api.ts:3236
- **Issue:** useGameControl's shared rollback(ctx) restores a per-call snapshot (ctx.prev) captured at that mutation's onMutate time. score/clock/segment/stats have no onSettled invalidation and no mutationKey/serialization. If two mutations for the same game are in flight (e.g. two rapid taps, or an operator + a co-operator on another device, or a score tap racing a clock action) and the FIRST one to be issued fails (network blip) while the SECOND one already succeeded and wrote the server-confirmed state via onSuccess: writeBack, the first mutation's onError fires rollback(ctx) with its OWN stale ctx.prev — snapshotted before either mutation ran — clobbering the cache back to a value that predates the second mutation's now-confirmed server truth.
- **Scenario:** Operator taps +1 twice quickly on a flaky venue Wi-Fi connection (CLAUDE.md itself notes 300-900ms RTT is normal here). Tap 1's PATCH is issued, then dropped/times out. Tap 2's PATCH is issued and succeeds, writeBack sets the cache to the true server score (e.g. 7). Tap 1's promise then rejects; onError calls rollback(ctx) with ctx.prev = the score from BEFORE either tap (e.g. 5). The scoreboard now optimistically shows 5 — wrong, and DECREASING after a successful increment — visible on the live board/ribbon until the next 4s poll silently corrects it. Same mechanism applies to clock/segment/stats mutations sharing the identical rollback closure.
- **Fix:** Either (a) add onSettled: () => qc.invalidateQueries({queryKey: gameKey}) to each of score/clock/segment/stats so a failed mutation's rollback is immediately superseded by a fresh server fetch rather than trusting a stale local snapshot, or (b) make rollback a no-op when the mutation's own body/timestamp is stale relative to the cache's current updatedAt (only roll back if the cache still matches what this mutation optimistically wrote), or (c) serialize same-resource mutations with a shared mutationKey so React Query only has one in-flight write per game at a time.

### [P1] apps/web/src/app/[schoolId]/sports/[gameId]/LanePadSection.tsx:202
- **Issue:** The 800ms debounced provisional stats PATCH and nextHeat()'s finalize PATCH are two independent, unserialized ctl.stats.mutate calls against the same PATCH /sports/games/:id/stats endpoint, which does a whole-array replace of stats.results (not an element-wise merge) server-side. cancelProvisionalTimer() only cancels a timer that hasn't fired yet; it cannot cancel a PATCH that the timer already dispatched a moment earlier.
- **Scenario:** Operator is mid-heat-entry; the 800ms debounce fires and ctl.stats.mutate({stats:{results: provisional}}) is sent (now in flight, un-cancelable). Within the next few hundred ms, the operator taps 'Next heat', which computes and sends a SECOND, different results array from a fresh (correct) base. If the network reorders the two requests (or the provisional's request is slow due to a retry/backoff) so the provisional PATCH's response/write lands on the server AFTER the finalize PATCH's, the finalize save is silently overwritten by the stale provisional snapshot — losing the just-saved heat's DQ/SCR/marks on the shared stats.results array.
- **Fix:** Give the provisional write a per-request monotonic sequence number (or timestamp) and have the server (or an onMutate check) ignore/coalesce an incoming results PATCH that is older than the last-applied one for this game, or move to a mutationKey-scoped queue so LanePadSection's provisional and finalize writes for the same game never race on the wire.

### [P2] apps/web/src/app/[schoolId]/sports/[gameId]/page.tsx:5610
- **Issue:** MeetResultsSection's updateEntry/updateEvent/write() close over `events`, an array derived fresh from props once per render. Two ResultsGridTextInput/ResultsGridNumberInput commits (e.g. via Tab-key navigation between adjacent cells) that both fire their onBlur commit handlers within the same browser task — before React has re-rendered the component with the first commit's optimistic cache update — will both compute their full stats.results array from the SAME stale `events` snapshot. The second write() overwrites the whole results array server-side, silently dropping the first field's just-typed edit.
- **Scenario:** An operator fast-tabs across a results row (Place -> Name -> Mark), typing a value and pressing Tab in each cell quickly enough that no re-render occurs between two consecutive blur/commit pairs. The second cell's write() call is built from an `events` array that doesn't yet include the first cell's edit, so the resulting full-array PATCH silently reverts the first cell back to its pre-edit value once it lands (or once a later poll reconciles).
- **Fix:** Have write() read the LATEST results from the query cache at commit time (qc.getQueryData) rather than from the render-time `events` closure, or apply each field edit as a targeted deep-merge patch server-side keyed by event/entry index instead of a full-array replace.

### [P1 · PROD] apps/api/src/templates/templates.controller.ts:2487
- **Issue:** POST :id/versions/:versionId/restore has NO staleness check (assertNotStale is never called), even though it performs the exact same destructive delete-all-zones-and-recreate + metadata overwrite as replaceZones/update, which DO carry the C2 guard. ### [P2] apps/api/src/templates/templates.controller.ts:252
- **Issue:** snapshotVersion's doc comment (line 236: 'in the SAME transaction so the cap can never observably slip') does not match the implementation: it is three sequential, non-atomic awaits (create, then findMany, then deleteMany) with no $transaction wrapper, unlike the doc's explicit claim.
- **Scenario:** Two saves on the same template land within milliseconds of each other (two tabs, or a very fast double-save from two operators). Both snapshotVersion calls run their create/findMany/deleteMany sequences concurrently and can interleave: e.g. both compute 'rows beyond position 5' from a row-count snapshot taken before the other's insert/delete lands, so the template can end up retaining 6 versions (cap slipped up) or occasionally evicting one extra (down to 4) in a worst-case race. It is best-effort and wrapped in try/catch (matches audit()'s discipline), and it never touches the live Template/TemplateZone rows, so no user-facing data is at risk — only the retention-count invariant the doc comment asserts is not actually held.
- **Fix:** Either wrap create+findMany+deleteMany in this.prisma.client.$transaction(...) to match the doc comment, or soften the comment to describe the actual best-effort (non-atomic, self-healing) semantics.

### [P2] apps/web/src/components/template-builder/BuilderShell.tsx:189
- **Issue:** The C1 draft-recovery check (isDraftNewer(draft, template.updatedAt)) runs against the useTemplate(id) React Query result, which has staleTime: 60_000 (apps/web/src/hooks/use-api.ts ~line 1098) and the global QueryClient default refetchOnWindowFocus: false — so on a remount within that 60s window the effect can compare the local draft against a CACHED (client-stale) server updatedAt rather than a freshly-fetched one.
- **Scenario:** Same browser: operator opens Template X (fetches updatedAt=T0, cached 60s), navigates away, another tab/device saves a change (server now T1>T0), operator navigates back into the SAME template within the 60s cache window before any invalidation happens — React Query serves the T0-cached template with no network refetch, so isDraftNewer compares against T0 instead of T1 and can incorrectly offer to 'Restore' a locally stale draft. - **Fix:** Add refetchOnMount: 'always' (or an explicit invalidate/refetch on builder-route mount) to useTemplate so the draft-recovery check always compares against a live-fetched updatedAt, not a cached one.


## Migration & schema safety — 2 migrations merged 2026-07-02, applied by Railway migrate deploy on the live pilot DB: 20260702090000_add_game_scheduled_at (Game.scheduledAt, S4) and 20260702120000_add_template_versions (TemplateVersion, Wave C)

Both migrations are clean and safe to apply on the live pilot DB. Full line-by-line cross-check against schema.prisma found zero discrepancies.

MIGRATION 1 — 20260702090000_add_game_scheduled_at/migration.sql:
- `ALTER TABLE "games" ADD COLUMN IF NOT EXISTS "scheduled_at" TIMESTAMP(3)` — nullable, no default, no backfill needed. Matches `scheduledAt DateTime? @map(\"scheduled_at\")` on Game (schema.prisma:2205) exactly — type, nullability, and snake_case mapping all correct.
- `CREATE INDEX IF NOT EXISTS \"games_tenant_id_scheduled_at_idx\" ON \"games\"(\"tenant_id\", \"scheduled_at\")` matches `@@index([tenantId, scheduledAt])` (schema.prisma:2230) exactly. Index name doesn't collide with the pre-existing `games_tenant_id_status_idx` (from 20260516000000_add_sports_games) or `games_tenant_id_scheduled_at_idx`'s sibling from 20260702080000_add_game_status_clock_running_index — checked all three migrations touching `games` and found no duplicate index names.
- CREATE INDEX on a populated `games` table takes a table lock by default (non-CONCURRENTLY), but the `games` table is small (per-game rows, not per-tick), so this is a non-issue in practice; not flagged as a real risk.
- Strictly additive: no DROP, no ALTER of an existing column, no NOT NULL-without-default trap. Every existing Game row gets NULL, which the app already treats as \"no scheduled time set\" per the migration's own comment and consistent with how Game's other nullable DateTime columns (startedAt, endedAt) are already handled.
