# AI Signage Generation Pipeline — Persisted vs Lost Map (for a learning loop)

Read-only research, code-verified against `apps/api/src/templates/templates.controller.ts`, `apps/api/src/ai/ai.service.ts`, `apps/api/src/ai/art-director.ts`, `packages/api-types/src/index.ts`, and `packages/database/prisma/schema.prisma`.

## Architecture in one paragraph

There are two AI generation families. (1) **Legacy touch-template** path: the LLM emits raw zone JSON directly (`TOUCH_TEMPLATE_SYSTEM_PROMPT`), sanitized by `sanitizeTouchTemplate`. (2) **Art-director engine** path (the flagship): the LLM emits ONLY an `ArtDirectorSpec` (archetype + theme + copy + image plan + accentSlot, NO geometry), and `artDirectorSpecToTemplate` (art-director.ts) runs the `@cms/signage-design` engine to produce zones. Both end at the shared persist helper `persistGeneratedTemplate` (controller line 1303). Candidates from the engine path carry their `spec` back to the FE (the only place the spec survives a round-trip); the legacy path does not.

The **central finding for a learning loop**: every generation writes a privacy-scrubbed `AuditLog` row with *dimensions* (archetype/theme/vertical/provider/zoneCount) but **never the prompt/intake, never the spec, never which candidate of N was kept, and never an outcome link**. The chosen-candidate index, the rejected candidates, the spec→outcome tuple, and post-keep edits are all LOST. The `AI_*` AuditLog rows and the persisted `Template` row exist but are **not joined by any id** — there is no `templateId` on the generation audit rows and no `generationId`/`specHash` on the Template.

## What is structurally LOST across the whole pipeline (the learning-loop gaps)

1. **Which candidate of N was kept** — the #1 missing signal. `generate-touch/candidates` returns N drafts; `create-from-candidate` persists one with **no index, no batch id, no "rejected the other N-1"**. The two events aren't even correlated (no shared id). `AI_SIGNAGE_BOARD_CANDIDATES.details.archetypes` logs the slate of archetypes offered, but nothing logs which archetype/board won.
2. **The intake → spec → outcome tuple** — `ConciergeIntake` + `brief` (chat) and `GuidedIntake` (purpose/theme/palette/background/widgets) are computed and used but never stored. The `ArtDirectorSpec` (the model's full creative decision) survives only in HTTP responses; it is read in `create-from-candidate` (`candidate.spec`, controller `:1147`) and then **dropped on the floor at persist** — `persistGeneratedTemplate` has no spec parameter.
3. **The prompt** — deliberately never logged (PII policy: comments at `ai.service.ts:858`, `:1357`). Only `promptLen` for images. A learning loop needs a consented/hashed prompt store; today there's zero.
4. **Post-keep edits to the kept board** — land in `PUT :id` (changedFields keys) and `PUT :id/zones` (zoneCount). Neither knows the template was AI-born, so "operator generated then heavily rewrote the headline" is invisible — the strongest negative-quality signal in the product.
5. **Publish-to-screen / playlist** — AI boards reach screens only via Playlist + Schedule (a separate controller, not in scope here). There is **no link from a Template to "it got published"** in the template/AI audit trail; the generation audit row's `targetId` is the tenant, so you can't ask "of AI boards generated, how many ever went live?"
6. **Discard/delete** — `TEMPLATE_DELETED` records name+category, not AI-origin or age, so churn of AI output is unmeasurable.

## Precise hook points to record each learning signal (file:function:line)

### (a) Which candidate of N was kept
- **Emit a batch id at fan-out.** `AiService.generateSignageBoardCandidates` (`ai.service.ts:2281`) and `generateTouchTemplateCandidates` (`ai.service.ts:1767`): mint a `candidateBatchId` (e.g. `randomUUID()`, already imported `ai.service.ts:30`), stamp it into the `AI_SIGNAGE_BOARD_CANDIDATES` / `AI_TEMPLATE_CANDIDATES` audit details (`ai.service.ts:2400` / `:1899`), and return it on each candidate object (response built at `ai.service.ts:2412`). The FE already passes the candidate back; add `batchId` + `chosenIndex` to it.
- **Record the choice at keep.** `TemplatesController.createFromCandidate` (`templates.controller.ts:1106`) — read `body.candidate.batchId` + a `chosenIndex`/`chosenArchetype` and write them into the existing `TEMPLATE_CREATED` audit call at `templates.controller.ts:1186` (add `batchId`, `chosenIndex`, `archetype: candidate?.archetype` to the details object). Requires adding `batchId`/`chosenIndex` to `TemplateCreateFromCandidateSchema` (`packages/api-types/src/index.ts:774`) — additive `.optional()` fields, no DB migration.

### (b) Full intake → spec → outcome tuple
- **Persist the spec onto the board.** `TemplatesController.persistGeneratedTemplate` (`templates.controller.ts:1303`) is the single chokepoint for every AI create. Add an optional `genMeta` param ({ spec, archetype, theme, batchId, chosenIndex, intake, source, model }) and write it. Two additive options, both schema-additive (live-pilot safe):
  - **Cheapest:** stash it in the existing `Template.brandKit` Json column? — NO, that's brand data; instead add a new nullable Json column `Template.aiGenMeta` (`schema.prisma:1139`, additive). 
  - **Preferred (decoupled, survives delete):** a new additive `AiGeneration` table modeled exactly on `TouchEvent` (`schema.prisma:1325`) — no FKs to Template so it survives edits/deletes, opaque `templateId` string, columns for `prompt`/`promptHash`, `intakeJson`, `specJson`, `archetype`, `theme`, `batchId`, `chosenIndex`, `provider`, `model`, `source`, `outcome`. The `TouchEvent` precedent (`schema.prisma:1316` comment: "Schema is additive. NO foreign keys… must survive a template edit/delete") is the exact pattern to copy and is explicitly endorsed in-repo.
- **Capture intake/brief at the chat boundary.** `AiService.conciergeChatInner` (`ai.service.ts:1259`), at the audit write `ai.service.ts:1359` — `turn.intake` and `turn.brief` are in scope (from `parseConciergeTurn`, `:1342`) but only `ready` is logged. Add them (with a PII decision) to the row or the new table.
- **Capture the spec on every engine generate.** `generateSignageBoardInner` (`ai.service.ts:1981`, spec at `:2030`), `generateSignageBoardCandidates` (`spec` per candidate `:2412`), `generateSignageBoardSet` (`core.spec` `:2571`), `refineSignageBoard` (`spec` `:2672`). All already hold the `ArtDirectorSpec`; today only `archetype`/`theme` reach the audit row.

### (c) Post-keep edits to the kept board
- **Flag AI origin so edits are attributable.** Add nullable `Template.createdVia` (string: `ai-touch|ai-candidate|ai-signage|preset|duplicate|blank|import`) at `schema.prisma:1139` (additive); set it in `persistGeneratedTemplate` (`templates.controller.ts:1324` create call) and the other create sites (`from-preset` `:1579`/`:1624`, `duplicate` `:1717`, `create` `:813`).
- **Record the edit deltas.** `TemplatesController.replaceZones` audit (`templates.controller.ts:2015`) and `update` audit (`:1917`): include `createdVia` and a coarse change descriptor (e.g. which zones' text changed) so "AI board, headline rewritten within 2 min of keep" is queryable. Both already write `TEMPLATE_UPDATED`; this is enriching existing details.

### (d) Publish-to-screen / playlist
- Out of this file set (Playlist/Schedule controllers). The hook is wherever a Playlist binds `templateId` to a Schedule. To make AI boards measurable, the new `AiGeneration` row (b) should get an `outcome`/`firstPublishedAt` updated when its `templateId` first appears in a Schedule — i.e. add a write in the schedule-create path (not in scope here) that does `UPDATE AiGeneration SET outcome='published' WHERE templateId=…`. Today **no such link exists.**

### (e) Delete / discard
- `TemplatesController.remove` (`templates.controller.ts:2026`), audit at `:2039`. Add `createdVia` (from the new column) and `ageMs = Date.now() - template.createdAt` to the `TEMPLATE_DELETED` details so discard-rate of AI boards is computable. If using the `AiGeneration` table, also `UPDATE … SET outcome='deleted'` keyed on the opaque `templateId` (survives the cascade because there's no FK).

## Additive-schema safety note (live pilot)
Every proposal above is **additive only**: new nullable columns (`Template.aiGenMeta`/`createdVia`) and/or a brand-new `AiGeneration` table with no FKs (mirroring `TouchEvent` at `schema.prisma:1325`). No `ALTER`/drop of existing columns, no change to the immutable `AuditLog` schema (`schema.prisma:1098`) — the cleanest path is the dedicated `AiGeneration` table so the immutable, legally-significant `audit_logs` (which has a DB-level immutability trigger per task #210) is not overloaded with mutable outcome fields.
