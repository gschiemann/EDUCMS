## Step-by-step what I did

1. **Located the a11y CI + baseline.** Read `.github/workflows/a11y.yml` (runs `pnpm a11y:ci` on every push to master + PRs), the runner `apps/web/scripts/a11y-audit.ts`, and the ratchet file `apps/web/scripts/a11y-warning-baseline.json`.
2. **Confirmed the ratchet is a real number, not 999.** Baseline = **1**, locked 2026-05-31, with an explicit note that "the 999 bootstrap ceiling is retired." Task #213's concern is closed and has not drifted back.
3. **Verified the gate logic** in `a11y-audit.ts`: fails CI on ANY error-level (critical/serious) violation, AND on `totalWarnings > warningBaseline` (down-only ratchet). 10 routes audited including `/panic`, `/[seed]/emergency/broadcast`, `/[seed]/screens?view=map`.
4. **Pulled live CI results.** Latest two **pushes to master are green** (`06038352`, `cfc44bff`). Read the green master run log: `axe-core results: 0 error(s), 1 warning(s) (baseline: 1)` → `✓ axe check passed.` The recent PR *failures* failed at the **"Install Dependencies"** step (axe never ran — `0` "Auditing http" lines) — an infra/lockfile issue, not an a11y regression.
5. **Emergency live-regions — read every surface.** `EmergencyLiveRegion.tsx` (shared `role="status" aria-live="assertive" aria-atomic="true"` + best-effort Web Speech), confirmed it's both *imported and rendered* (`{liveRegion}`) in the broadcast console (`broadcast/page.tsx:239`) and the trigger modal (`EmergencyTriggerModal.tsx:162`), with `announce(...)` fired on every state transition (hold/send/success/failure/cancel/clear). The panic page has its own equivalent inline live region + `announce()` + button `aria-label`.
6. **Keyboard-only nav on the panic page.** Hold-to-trigger button has `onKeyDown`/`onKeyUp` (Space/Enter starts the 3-s hold, ignores key-repeat, `preventDefault`) and `onBlur={clearHold}` (no keyboard trap). `aria-label` on each trigger button.
7. **Fleet-map color-blind safety.** `ScreenMap.tsx` — each status carries a **distinct Lucide shape icon** (`AlertTriangle`/`Wifi`/`WifiOff`/`MonitorPlay`) plus color, every pin has `role="img" aria-label="${label}"`, explicit "WCAG 1.4.1 icon-shape pins (color is never the only signal)" comment + on-map legend. Cluster bubbles inherit the worst-status color.
8. **Brand-palette contrast enforcement.** Server `apps/api/src/branding/color-utils.ts` has `ensureContrast()` (binary-searches lightness until ≥4.5:1 AA), `derivePalette(..., contrastTarget=4.5)`, and `enforcePaletteContrast()` wired into the live adopt path (`branding.controller.ts:294,1064`). The wizard additionally renders a live contrast grid grading each pair AAA/AA/AA-large/fail with failures in red (`BrandingWizard.tsx:1048-1056`). This is *enforcement* (colors are auto-nudged), not just a warning.
9. **Live-prod spot checks.** `/panic` and `/login` both return 200 with `<html lang="en">` (WCAG 3.1.1). Panic page `<title>` resolves to `EMERGENCY TRG`.

## Coverage — what I could NOT reach + why

- **Live SR/keyboard run inside the authed dashboard.** Read-only mandate + no test login meant I could not drive a screen reader or Tab through the live triggered emergency console / builder. I verified the announcer wiring and keyboard handlers by code-read and confirmed the green axe run, but the *rendered authed DOM* is exactly the CI gap in Finding #1 — neither I nor CI exercise it. Recommend a one-time manual VoiceOver/NVDA pass on a seeded tenant before GA (and as the natural fix for Findings #1/#2: auth the harness + add the builder route).
- **Did not run axe locally** (no `pnpm build`/Playwright per ground rules) — relied on the live green master CI run, which is authoritative for the shipping branch.
