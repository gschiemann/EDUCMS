### 3. [P1] Webhook retry claim strands PENDING deliveries forever if the pod dies mid-drain (no reclaim of next_retry_at=NULL rows)

- **File:** `apps/api/src/webhooks/webhook-retry.worker.ts:104`
- **Class:** cron/background-service consistency — crash-between-claim-and-apply leaves rows permanently unretriable (silent loss of the emergency webhook the subsystem exists to protect)

**Failure scenario:** WebhookRetryWorker.drainOnce() first runs an atomic claim UPDATE that sets `attempts = attempts + 1, next_retry_at = NULL, updated_at = NOW()` on a batch of up to 50 due rows (lines 104-120), THEN processes each row and calls dispatch.applyOutcome() to re-arm next_retry_at (line 164). The re-arm is the ONLY thing that puts a still-failing row back into the due set. ### 5. [P2] Service-worker activate copy-forward selects the 'newest' stale cache with lexical .sort(), which mis-orders at v10 (v10 < v9 as strings)

- **File:** `apps/web/public/sw-player.js:100`
- **Class:** stale/wrong emergency+playlist cache copied forward on SW version bump
- **Confirm votes:** 2/2

**Failure scenario:** On a VERSION bump, activate copies the previous version's EMERGENCY/META/PLAYLIST entries into the new versioned caches before deleting the old ones, choosing the source as the lexically-last stale cache name: `staleEmergency.sort(); oldEmergencyName = staleEmergency[staleEmergency.length-1]` (sw-player.js:100-102, :149-150). The comment asserts 'versioning is monotonic vN where N grows' and relies on string ordering. String sort breaks once N reaches two digits: 'edu-player-emergency-v10' sorts BEFORE 'edu-player-emergency-v9' (because '1' < '9'). If a kiosk ever holds two stale emergency caches at upgrade time (e.g. it installed v9's SW but its activate was killed/never completed, then v11 installs so both v9 and v10 remain), .sort() yields ['...-v10','...-v9'] and picks '...-v9' (the OLDER cache) as the copy-forward source, then deletes both. The new cache is seeded from the stale/emptier v9 set, leaving a brief window with fewer cached emergency assets until the next 5-min refreshEmergencyCache repopulates it. Masked in the common single-stale-cache upgrade path (the prior activate deletes all older caches at :168, so usually exactly one stale cache exists and 'last of one' is always right), which is why it hasn't surfaced — but it is a genuine ordering defect that activates the day VERSION crosses v9->v10.

**Code evidence:** sw-player.js:100-102 `const staleEmergency = stale.filter((k) => k.startsWith('edu-player-emergency-')).sort(); ... oldEmergencyName = staleEmergency.length ? staleEmergency[staleEmergency.length - 1] : null;` — lexical sort of 'v9'/'v10' is numerically inverted; current VERSION is 'v9' (sw-player.js:62), so the next bump enters the broken range.

**Verifier 1:** The code matches the claim exactly. sw-player.js:100-103 does `staleEmergency.filter(...).sort()` then picks `staleEmergency[staleEmergency.length-1]` as the copy-forward source, and the same pattern at :149-150 for playlist. Cache names are only ever minted as `edu-player-{tier}-${VERSION}` with `VERSION='v9'` (line 62), a single-letter+integer format, and the comment (line 99) explicitly relies on "string ordering — versioning is monotonic vN where N grows". Lexical `.sort()` is numerically inverted once N reaches two digits: `'edu-player-emergency-v10' < 'edu-player-emergency-v9'` is true because `'1' < '9'`, so `[length-1]` yields the v9 (OLDER) cache, not v10. No guard, numeric parse, or version-aware comparator exists anywhere in the path — line 168 then `caches.delete`s ALL stale caches, so the mis-selected-source data is lost.
