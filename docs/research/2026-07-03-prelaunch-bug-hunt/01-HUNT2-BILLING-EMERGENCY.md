### 1. [P0] A failed-payment webhook is silently swallowed (tenant stays ACTIVE without paying) because a newer benign quantity-sync event advanced the single shared out-of-order watermark.

- **File:** `apps/api/src/billing/stripe.service.ts:680`
- **Class:** webhook event ordering / failed payment not downgrading
- **Confirm votes:** 2/2

**Failure scenario:** All four License-mutating handlers (syncLicenseFromSubscription, applySubscriptionDeleted, applyPaymentFailed) gate on ONE shared column License.stripeLastEventCreatedAt and skip any event whose event.created is older than the stored value. But quantity-only 'customer.subscription.updated' events are fired constantly by our own self-heal: syncSubscriptionQuantity() runs on every screen pair/unpair/delete (screens.controller.ts:1236,1238,1338,2365) and on every /billing/invoices page load (billing.controller.ts:113), each calling stripe.subscriptionItems.update() which makes Stripe emit a customer.subscription.updated. Concrete sequence: (1) tenant's renewal invoice fails -> Stripe mints invoice.payment_failed at created=150. (2) Before that event is delivered/processed, an operator pairs a screen -> syncSubscriptionQuantity fires -> Stripe emits customer.subscription.updated at created=200 -> syncLicenseFromSubscription applies it (status active -> ACTIVE) and stamps stripeLastEventCreatedAt=200. (3) The delayed invoice.payment_failed (created=150) now arrives at applyPaymentFailed; the guard at lines 680-690 sees 200 > 150 and returns {staleOutOfOrder:true} WITHOUT setting PAST_DUE. Result: the tenant whose card was declined keeps a fully-ACTIVE license indefinitely — the downgrade is permanently lost, not retried (Stripe got a 200). Money loss: unpaid tenant retains paid service. Stripe does NOT guarantee cross-object event ordering, so this reorder is a normal occurrence, and our own webhook-triggering self-heal makes benign newer events routine.

**Code evidence:** applyPaymentFailed lines 680-690: `if (license.stripeLastEventCreatedAt && license.stripeLastEventCreatedAt.getTime() > eventCreatedAt.getTime()) { ...return { staleOutOfOrder: true }; }` — the watermark is a single per-License field written by EVERY handler (line 697 sets status PAST_DUE + stripeLastEventCreatedAt; line 534/545 in syncLicenseFromSubscription writes the same field for quantity-only updates). A quantity-sync update (which carries status:'active') both advances the watermark AND cannot be told apart from a real status change, so it legitimately blocks a genuinely-newer-in-intent but earlier-timestamped payment_failed. Verified there is no invoice.payment_succeeded/invoice.paid handler (grep of stripe.service.ts) so PAST_DUE recovery relies entirely on subscription.updated — meaning the same shared-watermark reorder also blocks recovery in the mirror case.

### 2. [P0] checkoutForTenant never checks for an existing active subscription, so a second 'Subscribe' creates a duplicate Stripe subscription that double-bills the customer and is then orphaned when the License row's single stripeSubscriptionId is overwritten.

- **File:** `apps/api/src/billing/stripe.service.ts:233`
- **Class:** proration/duplicate-subscription drift between Stripe and the License row
- **Confirm votes:** 2/2

**Failure scenario:** A DISTRICT_ADMIN/SCHOOL_ADMIN who already has a live subscription hits Settings -> Billing -> Subscribe again (e.g. to 'switch from monthly to annual', or just double-clicks, or re-subscribes after thinking it didn't take). checkoutForTenant (lines 229-243) loads the License, reuses license.stripeCustomerId, but NEVER checks license.stripeSubscriptionId / the customer's existing active subscriptions before creating a brand-new mode:'subscription' Checkout Session. When that second checkout completes, checkout.session.completed -> syncLicenseFromSubscription runs its upsert whose UPDATE branch (lines 536-547) unconditionally sets `stripeSubscriptionId: sub.id` to the NEW subscription id. The FIRST subscription is now orphaned: it still exists and keeps generating invoices/charges every period on the same customer, but no License row references it, so the tenant is billed twice. The daily reconcile cron (license-reconcile.cron.ts) only iterates License.stripeSubscriptionId, so it can never see or clean up the orphaned sub — the double-billing is permanent until a human notices in the Stripe dashboard. Concrete money loss: 2x (or Nx on repeated clicks) the intended per-screen monthly/annual charge, indefinitely.

**Code evidence:** Lines 233-243: `stripe.checkout.sessions.create({ mode: 'subscription', line_items: [{ price, quantity }], ... ...(license?.stripeCustomerId ? { customer: license.stripeCustomerId } : {}), ... })` — no read of license.stripeSubscriptionId, no `stripe.subscriptions.list({customer, status:'active'})` guard, no early-return that would send an existing subscriber to the Customer Portal instead of a fresh Checkout. The License schema has a single scalar `stripeSubscriptionId String? @map("stripe_subscription_id")` (schema.prisma:566), and syncLicenseFromSubscription's update block (line 542) overwrites it every time, so the first subscription's id is lost. Confirmed no controller-level guard: billing.controller.ts checkout() (lines 57-82) calls checkoutForTenant directly with only role + stripe.enabled() checks.

**Verifier 1:** I tried to find a guard one layer up and found none. checkoutForTenant (apps/api/src/billing/stripe.service.ts:214-246) loads the License and reuses license.stripeCustomerId (line 237) but has NO read of license.stripeSubscriptionId, NO stripe.subscriptions.list({customer,status:'active'}) check, NO early-return to the portal, and NO idempotency key on the create() call. The controller checkout() (billing.controller.ts:57-82) only checks role + stripe.enabled() and calls checkoutForTenant directly — no guard there. The schema field is a single scalar (schema.prisma:566: stripeSubscriptionId String?), and syncLicenseFromSubscription's upsert update branch (stripe.service.ts:542) unconditionally sets stripeSubscriptionId: sub.id, overwriting the first sub's id on the second checkout.session.completed. Stripe allows multiple concurrent active subscriptions to the same price/customer, so the second completed checkout is a real second recurring charge. The only nuance: a bare double-click doesn't auto-charge (it opens a hosted page that must be submitted); the money loss triggers on the 'switch plan / re-subscribe' completion path the scenario names. Defect is real, reproducible, permanent, and self-healing never catches it.

**Verifier 2:** I read every layer trying to find an existing-subscription guard and found none. checkoutForTenant (stripe.service.ts:214-246) loads the License and reuses license.stripeCustomerId but never reads license.stripeSubscriptionId and never calls stripe.subscriptions.list({customer,status:'active'}); there is no early-return to the Customer Portal. ### 3. [P1] Stripe webhook out-of-order guard is a TOCTOU: the freshness check reads stripeLastEventCreatedAt outside the transaction, so two concurrently-processed events for one tenant can commit the OLDER state last, silently corrupting billing/license state.

- **File:** `apps/api/src/billing/stripe.service.ts:496`
- **Class:** read-modify-write race (TOCTOU) with insufficient isolation
- **Confirm votes:** 2/2

**Failure scenario:** Stripe delivers two ordered events for the same tenant close together — e.g. customer.subscription.updated (event A, event.created=T, status still ACTIVE) and invoice.payment_failed / customer.subscription.deleted (event B, event.created=T+5s, status PAST_DUE/CANCELLED). They have distinct event.ids, so BOTH pass the INSERT-first idempotency ledger at line 336 (that gate only dedups the SAME id, never serializes different ids). Two API replicas (Railway runs multiple) each pick one. Replica-2 (event A) and replica-1 (event B) both call syncLicenseFromSubscription/applySubscriptionDeleted and both read `existing.stripeLastEventCreatedAt` at line 496 (resp. 591) while it still holds the old value T-60s — so BOTH pass the freshness comparison at lines 505-508 (resp. 601-604). Replica-1 commits B's newer state (e.g. status=CANCELLED, stripeLastEventCreatedAt=T+5s). Replica-2 then commits A's OLDER state inside its Read-Committed `$transaction` (line 520), overwriting status back to ACTIVE and stripeLastEventCreatedAt back to T. The transaction re-reads nothing and takes no row lock on the guard column, so last-writer-wins. Result: a cancelled/past-due subscription persists as ACTIVE (tenant keeps full paid seat entitlement for free) or an active one persists as CANCELLED (tenant's screens get locked out) — and stripeLastEventCreatedAt is now stale, so future correctly-ordered events may also be mis-evaluated.

**Code evidence:** Line 496-508: `const existing = await this.prisma.client.license.findUnique({ where: { tenantId }, select: {..., stripeLastEventCreatedAt: true} }); if (existing?.stripeLastEventCreatedAt && existing.stripeLastEventCreatedAt.getTime() > eventCreatedAt.getTime()) { ...return { staleOutOfOrder: true }; }` — the read is OUTSIDE the write transaction. Line 520 `await this.prisma.client.$transaction(async (tx) => { const license = await tx.license.upsert({...stripeLastEventCreatedAt: eventCreatedAt...}) })` passes no isolationLevel, so it defaults to Read Committed and does NOT re-verify the guard or lock the row against a concurrent handler that read the same stale timestamp. The idempotency gate at line 336 (`processedStripeEvent.create` on unique event.id) only prevents re-processing the SAME event; it provides no ordering between DIFFERENT events for one tenant. applySubscriptionDeleted at lines 591-620 has the identical check-outside-tx / upsert-inside-Read-Committed-tx shape. Correct fix: move the read+guard+write into one Serializable/withDbRetry transaction (as screens.controller.pair already does for the seat race), or gate the upsert with a conditional `where: { stripeLastEventCreatedAt: { lt: eventCreatedAt } }`.

**Verifier 1:** I tried to refute the claim on four fronts and all failed. (1) Upstream serialization: billing-webhook.controller.ts processes each Stripe POST inline via handleWebhookEvent — no queue, no per-tenant lock, no mutex; Railway runs multiple replicas, so two events can be handled concurrently. (2) Idempotency ordering: the INSERT-first gate at stripe.service.ts:336 inserts on event.id and only rejects a DUPLICATE id (P2002); two DIFFERENT event ids both pass and it provides zero ordering between them (the code comments say exactly this). (3) In-transaction re-check/lock: the $transaction at line 520 (and 613, 692) passes NO isolationLevel — Prisma's default is Read Committed — takes no row lock (no SELECT FOR UPDATE), and the upsert/update carries NO conditional where:{stripeLastEventCreatedAt:{lt:eventCreatedAt}} guard. The freshness read is a plain findUnique at 496 OUTSIDE the tx (identical shape at 591-604 in applySubscriptionDeleted and 680-690 in applyPaymentFailed). (4) Global isolation: grep of apps/api/src/prisma found no global transactionOptions/isolationLevel. So the TOCTOU is real exactly as described: two replicas each read the same stale stripeLastEventCreatedAt (T-60s), both pass the freshness comparison, and the older event's $transaction can commit last under Read-Committed last-writer-wins — reverting status (e.g. CANCELLED→ACTIVE, so a cancelled tenant keeps paid entitlement, or ACTIVE→CANCELLED, locking a paying tenant out) AND poisoning stripeLastEventCreatedAt so subsequent correctly-ordered events are mis-evaluated. The guard was explicitly built to prevent this out-of-order corruption (see the 2026-05-26 P0-7 comments at 310-325) and the check-then-act window defeats it. The codebase already has the correct pattern (Serializable + withDbRetry in screens.controller.ts:1196) proving this handler simply lacks it.

**Verifier 2:** I tried to refute this by hunting for protection at every layer and found none. Confirmed from apps/api/src/billing/stripe.service.ts: (1) The freshness read + guard sit OUTSIDE the write transaction in all three mutating handlers — syncLicenseFromSubscription reads license.findUnique at 496 and checks stripeLastEventCreatedAt at 505-508; applySubscriptionDeleted reads findFirst at 591 and checks at 601-604; applyPaymentFailed reads findFirst at 670 and checks at 680-683. (2) The $transaction at line 520 (and 613, 692) passes ONLY a callback, no options — so it runs at Postgres default Read Committed and takes no lock on the guard column. (3) The upsert (521) keys on {tenantId} and the updates (614/693) on {id} — none carry a conditional `where: { stripeLastEventCreatedAt: { lt: eventCreatedAt } }`, so it's blind last-writer-wins. (4) The idempotency gate at line 336 (processedStripeEvent.create on unique event.id) only dedups the SAME id; two DIFFERENT event ids both pass, exactly as claimed. (5) The controller (billing-webhook.controller.ts) does NO serialization/locking around handleWebhookEvent, and CLAUDE.md confirms Railway runs multiple replicas with no distributed lock. Even the single-row UPDATE row-lock inside the tx does not save this: the guard was already evaluated before the lock was acquired, so the second writer blocks, then blindly overwrites with the older state (classic check-then-act across the lock boundary / lost update). Decisive corroboration: the codebase's OWN correct pattern for this exact class — screens.controller.ts:1196 — wraps the seat race in `isolationLevel: 'Serializable'` + withDbRetry; the billing path uses neither (grep confirms zero isolationLevel/withDbRetry in apps/api/src/billing). Two ordered events (updated→ACTIVE at T, then deleted/payment_failed→CANCELLED/PAST_DUE at T+5s) processed concurrently both read the pre-T stale timestamp, both pass the guard, and the older ACTIVE state can commit last — leaving a cancelled tenant ACTIVE (free paid seats) or an active tenant CANCELLED (screens locked out), plus a poisoned stripeLastEventCreatedAt that mis-evaluates future events. Reproduction is concrete and matches the claim exactly.
