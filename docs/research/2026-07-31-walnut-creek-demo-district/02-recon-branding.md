# Recon: Branding tool (scrape/adopt/apply)

## Summary
The auto-branding feature is a full module at apps/api/src/branding/: POST /api/v1/branding/scrape (JWT + admin roles, body {url}) returns a rich BrandingPreview (logos/colors/palette/fonts/heroImages/confidence), and POST /api/v1/branding/adopt persists it into the Prisma TenantBranding model (table tenant_branding — logoUrl, logoSvgInline, palette Json, fontHeading/fontBody, etc.), re-hosting logos into the public Supabase 'branding-logos' bucket via SupabaseStorageService.uploadLogo. A one-click POST /api/v1/branding/apply-to-templates re-skins every non-system template (bg gradient + per-zone defaultConfig color/fontFamily/accentColor, and a cfg.brand token map for EXTERNAL_HTML boards). The brand-contrast contract: raw --brand-primary is never repurposed as a workhorse shade — contrast-guaranteed derivatives (primaryMid/Strong/StrongHover/Stronger at ≥2.5/4.5/5.2/7 vs white, computed by ensureReadableOnWhite in apps/web/src/lib/brand-contrast.ts and persisted by enforcePaletteContrast server-side) feed the chrome; check-brand-contrast.cjs gates this. A Node script can drive the whole flow server-side: POST /api/v1/signup (returns access_token, no email gate — the authed-runner.mjs pattern) or POST /api/v1/auth/login with BETA_EMAIL/BETA_PW, then Bearer-token calls to scrape+adopt; adopt does all logo re-hosting and palette contrast enforcement server-side, so a script never needs to upload logos or compute shades itself.

## 3. applyToTemplates — POST /api/v1/branding/apply-to-templates (controller lines 737-875)

Roles: SUPER_ADMIN/DISTRICT_ADMIN/SCHOOL_ADMIN. Body: `{ mode?: 'fill-blanks' | 'override' }` (default 'fill-blanks' = only set unset keys; 'override' forces). Requires an existing TenantBranding row else 400 BRANDING_NOT_CONFIGURED. In one $transaction over all templates `where: { tenantId, isSystem: false }` (system presets EXCLUDED):
- Template background: if palette has distinct primary+accent → `bgGradient = linear-gradient(135deg, primary 0%, accent 100%)` + `bgColor = primary`; else `bgColor = palette.surface || surfaceAlt || primary || '#ffffff'`.
- Every TemplateZone.defaultConfig (JSON string) patched: `color` ← palette.ink (default '#0f172a'), `fontFamily` ← branding.fontHeading, `accentColor` ← palette.accent || palette.primary.
- Zones with `widgetType === 'EXTERNAL_HTML'` additionally get `cfg.brand` token map: keys `primary, accent, text, surface, background, muted, fontDisplay, fontBody` — forwarded by ExternalHtmlWidget as `?brand=` to the iframe shim's applyBrand() → --brand-* CSS vars (BRAND_MAP).
Returns `{ count, zonesPatched, mode, templates: [{id,name}], message }`. Audit action 'BRANDING_APPLY_TO_TEMPLATES'.

## 4. Brand-contrast contract (the VisionCore cream incident, 2026-07-21/22)

Files: apps/web/src/lib/brand-contrast.ts (pure, zero imports), apps/web/src/lib/branding.ts (cssVarsFromPalette line 193), apps/web/src/app/globals.css, gate apps/web/tools/check-brand-contrast.cjs, API side apps/api/src/branding/color-utils.ts (deriveReadableShades) + enforcePaletteContrast (controller lines 1188-1251).

THE CONTRACT a script must honor when setting brand colors directly:
1. `--brand-primary` / `palette.primary` stays the operator's color (post-WCAG-nudge) — it is NEVER used raw as a workhorse text/button shade. globals.css maps `--color-indigo-500/600 ← var(--brand-primary-strong, …)`, `--color-violet-600 ← var(--brand-accent-strong, …)`, `.text-brand ← --brand-primary-strong`; the gate asserts raw primary never feeds any 500+ Tailwind shade.
2. Workhorse shades are hue-preserving darkened derivatives vs WHITE: `primaryMid` ≥2.5:1, `primaryStrong` ≥4.5:1 (AA), `primaryStrongHover` ≥5.2:1, `primaryStronger` ≥7:1 (AAA); same 4 for accent. Computed by `ensureReadableOnWhite(hex, target)` (brand-contrast.ts line 57 — binary search on HSL lightness; already-passing dark colors return UNCHANGED; never returns #000).
3. `cssVarsFromPalette` PREFERS persisted values: `hex(pAny.primaryStrong) ?? ensureReadableOnWhite(pri, 4.5)` (branding.ts lines 219-228). So: a script writing `tenant_branding.palette` directly MUST either (a) omit the *Mid/*Strong/*StrongHover/*Stronger keys entirely (painter derives them safely at paint time), or (b) include CORRECT values — a persisted stale/wrong primaryStrong WINS over the painter's derivation and re-creates the invisible-chrome bug. The safest path is to go through the API adopt endpoints, where enforcePaletteContrast re-derives all shade fields from the FINAL adjusted primary/accent regardless of what the client sent (controller lines 1229-1238: `out[key+'Mid'|'Strong'|'StrongHover'|'Stronger'] = deriveReadableShades(base)`).
4. enforcePaletteContrast also nudges primary/accent to ≥4.5:1 against their auto-picked ink (`bestTextOn` → #fff or #0b1220), preserving originals in `primaryRaw`/`accentRaw` and stamping `primaryOn`/`accentOn`/`primaryInk`/`accentInk` + a `contrastReport` `{ target, adjustments[], anyAdjusted, anyCapped }`.
5. Gate: `node apps/web/tools/check-brand-contrast.cjs` (exit 1 on violation) — transpiles the real brand-contrast.ts, runs the literal incident palette (#fcf9e2 cream → deep gold, hue within 25° of #e9d42f, not black; healthy #116dff and #4f46e5 pass through unchanged), and source-pins branding.ts + globals.css wiring.

## 5. Server-side calls from a Node script + auth

- **Auth needed**: `/branding/scrape` and `/branding/adopt` need a JWT Bearer token whose user has role SUPER_ADMIN, DISTRICT_ADMIN, or SCHOOL_ADMIN (tenant scope comes from the token). `/branding/demo/scrape` needs NO auth (but 5/min/IP + 50/hr global, and strips rawSnapshot — fine for extraction-only, not adoptable to a tenant).
- **Pattern A — self-provision (authed-runner.mjs lines 68-102)**: `POST {API}/signup` with `{ districtName, slug, adminEmail, password, vertical, firstName, lastName }` → response `{ access_token, user }` (user.tenantSlug/tenantId). No email verification gate. Route defined at apps/api/src/onboarding/onboarding.controller.ts line 23 (`@Controller('api/v1')` + `@Post('signup')`). Signup throttled ~5/min (retry with backoff on 429 as the harness does).
- **Pattern B — login with existing creds (persona-runner.mjs lines 54-62)**: env vars `BETA_EMAIL` / `BETA_PW`; API route `POST /api/v1/auth/login` (auth.controller.ts line 29) body `{ email, password, rememberMe? }` (Zod LoginInputSchema, email ≤254, password ≤256), throttle 10/min/IP, returns the session envelope with access token (may be an `mfaRequired` envelope). Failed/successful attempts are audit-logged (AUTH_LOGIN_FAILED / AUTH_LOGIN_SUCCESS).
- **Live endpoints used by harnesses**: API `https://api-production-39a1.up.railway.app/api/v1`, web `https://venue-os.app` (authed-runner.mjs lines 18-20). Browser-side token storage keys: `edu_cms_token`, `edu_cms_user`, `edu_cms_remember` (line 28); prior sessions drove authed page-context fetches with `Bearer localStorage.edu_cms_token`.
- **Pattern C — direct DB (bypasses API auth)**: scripts/archive-test-tenants.cjs uses `pg` Client with `DATABASE_URL` auto-loaded from `apps/api/.env` (lines 20-31). CAUTION per CLAUDE.md: raw-SQL content writes bypass the Prisma $use manifest-cache invalidation hook (30-min TTL lag on players) — for branding that's dashboard-only, but prefer the API path which also runs contrast enforcement + audit logging.
- No CSRF concern for pure-Bearer script calls: the JSON API endpoints accept Authorization headers (harnesses call them with ctx.request/fetch directly).

## 6. Logo hosting / re-host helper

- Bucket: `branding-logos` (LOGO_BUCKET, supabase-storage.service.ts line 41) — PUBLIC bucket, allows `image/svg+xml` (the general `assets` bucket BUCKET does NOT — task #223). Auto-created/updated at API boot with its own size cap.
- `SupabaseStorageService.uploadLogo(filePath, buffer, contentType)` (line 311) → `uploadToBucket('branding-logos', …)` (line ~330) — talks to the Supabase Storage REST API directly via fetch using `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` env vars (deliberately NOT @supabase/supabase-js, which mangles Node Buffers into 0-byte files). Returns the public URL.
- Re-host from URL: private `BrandingController.rehostUrl(sourceUrl, keyPrefix)` (controller lines 964-982) — `safeFetch(sourceUrl, { maxBytes: 2MB, timeoutMs: 6000 })` (SSRF-guarded, apps/api/src/branding/safe-fetch.ts), rejects non-2xx and non-image bodies (`looksLikeImage` magic-byte sniff lines 1264-1277), path = `${keyPrefix}-${sha256(body).slice(0,12)}.${ext}`, then uploadLogo. Storage key conventions: `branding/${tenantId}/logo.svg`, `branding/${tenantId}/logo-<hash>.<ext>`, `branding/${tenantId}/manual-<hash>.<ext>`, `branding/${tenantId}/logo-upload-<hash>.<ext>`, `branding/${tenantId}/favicon-<hash>`, `branding/${tenantId}/og-image-<hash>`, per-template `branding/templates/${templateId}/…`.
- These rehost helpers are PRIVATE controller methods, not exported — a standalone script can't import them, but doesn't need to: **POST /api/v1/branding/adopt performs all re-hosting server-side** (scraped URL candidates, inline SVG dual-storage raw-to-bucket + sanitized-inline, data-URL uploads via `logoDataUrl`, favicon/ogImage). So the script-friendly flow is: login → POST /branding/scrape {url} → POST /branding/adopt with the returned preview (optionally overriding palette/displayName/logoOverride) → server re-hosts logo into branding-logos and persists a contrast-enforced palette. Alternatively POST /branding/me/manual with `logoUrl` (server rehosts, rejects .ico and non-images) or `logoDataUrl` (base64, 2MB cap).
