# Recon: Demo lifecycle + teardown

## Summary
scripts/archive-test-tenants.cjs is a raw-`pg` (not Prisma) script that soft-archives tenants: dry-run by default, `--apply` to archive everything not on a hard-coded 11-id KEEP list, `--restore <tenantId>` to unarchive one; each archive is a per-tenant transaction that inserts a TENANT_ARCHIVED audit_logs row then sets tenants.archived_at=now(). All three env files a root script can load (apps/api/.env, root .env, packages/database/.env) point DATABASE_URL at aws-1-us-east-1.pooler.supabase.com:6543 — the LIVE production Supabase pooler (this repo has one prod DB; V1 pilot runs on it), so any root-level script hits production. Reusable demo generators exist: SampleDataService (auto-seeds vertical-aware POS menus/retail SKUs/broadcaster streams/house ads at signup, all tagged "[Sample]"), packages/database/prisma/seed-multilocation-demo.mjs + seed-50-locations.mjs (full Acme Coffee chain with tenants/screens/menu catalog, additive+idempotent with --clean), and seed.ts (Springfield + 2 empty starter playlists) — but nothing currently seeds playlists-with-items or assets per vertical. Teardown MUST be archive-not-delete: hard tenant delete is architecturally impossible once any audit_logs row exists (FK RESTRICT + DB-level immutability triggers that block UPDATE/DELETE/TRUNCATE on audit_logs), and the API maps this to 409 TENANT_DELETE_HAS_HISTORY. Emergency wiring: Tenant.emergencyPlaylistId + 6 panic*PlaylistId + 7 portrait variants are all nullable and NOT seeded anywhere — they are lazily created by PanicContentController.ensurePlaylist as isProtected=true playlists when an operator first drops assets into a panic bucket, and every manifest/trigger path filters null ids safely, so demo tenants with no lockdown playlists break nothing and Greg's later messaging step just populates the buckets.

## Details
== 1. scripts/archive-test-tenants.cjs (the teardown model) ==
- DB connection: raw `pg` `Client` (`new Client({ connectionString: process.env.DATABASE_URL })`), NOT Prisma — no @prisma/client dependency, so it runs from repo root with just `pg` installed (lines 22, 61).
- Env resolution (lines 24-35): if `process.env.DATABASE_URL` unset, it reads, in order: `apps/api/.env` then repo-root `.env`; regex `^\s*DATABASE_URL\s*=\s*(.+)\s*$` per line, strips surrounding quotes; exits code 2 if still unset.
- Precondition guard (lines 64-66): queries information_schema.columns for tenants.archived_at; exits code 3 with "deploy the migration first" if absent (migration `20260723140000_tenant_archived_at`).
- Usage / flags (exact):
  - `node scripts/archive-test-tenants.cjs` — DRY RUN: prints `KEEP (n): ...` and `WOULD ARCHIVE (n):` with name+id per tenant, writes nothing.
  - `node scripts/archive-test-tenants.cjs --apply` — archives.
  - `node scripts/archive-test-tenants.cjs --restore <tenantId>` — single `UPDATE tenants SET archived_at=NULL WHERE id=$1 RETURNING name`.
- Selection (lines 74-78): `SELECT id, name, parent_id FROM tenants WHERE archived_at IS NULL AND id <> ALL($1::text[]) ORDER BY name` — i.e. archive everything NOT in the hard-coded `KEEP` Set (lines 42-54, 11 ids: System 00000000-...-000000000000, Springfield District ...0001, Springfield Elementary ...0002, Dodgers 28d09f9d-..., VisionCore 81554fbe-..., Goodview 88118f06-..., Chardon HS 2bf88a7b-..., Chardon MS 03e6cecb-..., Fremont 13d421aa-..., AGC e1ce74a1-..., ARC 7976439f-...).
- Apply loop (lines 88-104): per-tenant `BEGIN` → `INSERT INTO audit_logs (id, tenant_id, user_id, action, target_type, target_id, details, created_at) VALUES (gen_random_uuid()::text, $1, NULL, 'TENANT_ARCHIVED', 'Tenant', $2, $3, now())` with tenant_id = `t.parent_id || t.id`, details JSON `{name, via:'archive-test-tenants.cjs'}` → `UPDATE tenants SET archived_at=now() WHERE id=$1` → `COMMIT`; on error ROLLBACK + "! skipped" (batch continues). Mirrors the API archive endpoint's audit-in-same-transaction behavior.

== 4. Tenant child-row surface + why archive-not-delete ==
Tenant back-relations (schema.prisma model Tenant): assetFolders (AssetFolder), assets (Asset), auditLogs (AuditLog), bugs (Bug), playlists (Playlist), schedules (Schedule), screenGroups (ScreenGroup), screens (Screen), templates (Template), templateVersions (TemplateVersion), notifications, children (self-relation TenantHierarchy), users (User), ssoConfig, cleverSyncLogs, userInvites, sportsTeams, sportsPersons, playerSeasonStats, playerCareerStats, statRecords, statMilestoneDefs, playerMilestones, usbIngestEvents, games (Game), sponsors (Sponsor), license (License), branding (TenantBranding), submissions (Submission), floorPlans (FloorPlan), touchEvents (TouchEvent), apiKeys (TenantApiKey), webhooks (TenantWebhook). Plus posProviderConnection/posMenuItem, streamProviderConnection, adNetworkConnection, menuCatalog/menuItem/menuLocationOverride reached via tenantId (accessed as `(prisma.client as any)` in sample-data code).
- AuditLog.tenant FK has NO onDelete behavior declared (= RESTRICT default) and audit_logs has DB-level triggers: `audit_logs_immutable` (fn `audit_logs_block_mutation`, migration 20260609000000) blocks DELETE outright and blocks every UPDATE except the single user_id→NULL anonymization with all other columns byte-identical; `audit_logs_no_truncate` (fn `audit_logs_block_truncate`, migration 20260717120000) blocks TRUNCATE statement-level. Schema comment on Tenant.archivedAt: "Hard-delete is architecturally impossible for any tenant with audit history (audit_logs FK RESTRICT + the §16 immutability trigger)".
- API behavior confirming it: tenants.controller.ts catches Prisma P2003 on tenant delete → 409 `{code:'TENANT_DELETE_HAS_HISTORY'}`. Supported path = archive: `POST /api/v1/tenants/:id/archive`, `POST /api/v1/tenants/:id/unarchive`, `POST /api/v1/tenants/archive-bulk` — all @RequireRoles(AppRole.SUPER_ADMIN). setArchived guards: cannot archive the tenant you're currently in (`TENANT_CANNOT_ARCHIVE_CURRENT`), cannot archive mid-emergency (`TENANT_ARCHIVE_ACTIVE_EMERGENCY` unless emergencyStatus in CALM_EMERGENCY = ['', 'NORMAL', 'INACTIVE']); writes TENANT_ARCHIVED/TENANT_UNARCHIVED audit row in the same $transaction as the archivedAt update.
- Archive semantics: child rows are all LEFT IN PLACE; every fleet/switcher/locations/count query filters `archivedAt: null` (tenants.controller.ts:33,49,82; fleet per memory), tenant remains reachable by direct id for auth/unarchive/audit lineage. AuditLog rows block nothing under archive — they only block HARD delete.
- Teardown recipe therefore: (a) never delete audit_logs; (b) for demo tenants, either archive (reversible, zero-risk, matches archive-test-tenants.cjs) or, if真 row removal of demo children is wanted, delete children bottom-up by tagged/deterministic ids (the seed-multilocation --clean pattern) but SKIP auditLog deletion and finish with tenant ARCHIVE instead of tenant delete.

== 5. Emergency playlist wiring ==
- Tenant columns (schema.prisma, all `String?` nullable, default NULL): `emergencyPlaylistId` (generic/default bucket + also the CURRENTLY-ACTIVE playlist set atomically at trigger time), `panicLockdownPlaylistId`, `panicEvacuatePlaylistId`, `panicWeatherPlaylistId`, `panicHoldPlaylistId`, `panicSecurePlaylistId`, `panicMedicalPlaylistId`, plus portrait variants `emergencyPortraitPlaylistId`, `panicLockdownPortraitPlaylistId`, `panicEvacuatePortraitPlaylistId`, `panicWeatherPortraitPlaylistId`, `panicHoldPortraitPlaylistId`, `panicSecurePortraitPlaylistId`, `panicMedicalPortraitPlaylistId`. Screen model additionally carries per-screen Sprint-8b overrides `emergencyLockdownPlaylistId`...`emergencyMedicalPlaylistId` (+ portrait + `emergency*AssetUrl` columns).
- NOTHING seeds these: seed.ts creates only 2 empty content playlists; SampleDataService seeds no playlists at all; no seeder references panic*/emergency*PlaylistId. They are created LAZILY by `PanicContentController.ensurePlaylist(tenantId, kind, orientation)` (apps/api/src/panic-content/panic-content.controller.ts:100+) the first time an operator drops assets into a panic bucket via `/api/v1/panic-content` — it creates a Playlist row with `isProtected = true` and `protectedKind` = kind (landscape) or `${kind}_portrait`, then writes its id into the mapped Tenant column. Kind→field map (lines 36-44): lockdown→panicLockdownPlaylistId, weather→panicWeatherPlaylistId, evacuate→panicEvacuatePlaylistId, hold→panicHoldPlaylistId, secure→panicSecurePlaylistId, medical→panicMedicalPlaylistId, default→emergencyPlaylistId (portrait map at lines 49-57). ensurePlaylist SELF-HEALS: if a column points at a deleted or wrong-tenant playlist it re-creates a fresh one — so even a sloppy teardown that removed a protected playlist cannot permanently break the wiring.
- Null-safety downstream: the manifest emergency-asset resolver (screens.controller.ts:3774-3801) collects all 26 tenant+screen playlist-id fields and `.filter((x): x is string => !!x)` — null columns are simply skipped; a trigger with no matching playlist falls back to the built-in emergency template render. GET /api/v1/emergency status (emergency.controller.ts:78) likewise reads `t.panicLockdownPlaylistId ?? null`.
- Conclusion for the demo work: create demo tenants WITHOUT touching any emergency/panic columns (leave NULL — nothing breaks); Greg's later "lockdown messaging" step populates them himself through the panic-content UI. The only ways to break the wiring are (a) deleting Playlist rows where isProtected=true (self-heals but loses his content), or (b) writing bogus ids into the panic columns — do neither in seed or teardown. `PATCH`-style panic playlist assignment also exists in tenants.controller.ts (~lines 606-664, accepts panicLockdownPlaylistId etc.) — teardown should not call it.
