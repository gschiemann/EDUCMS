§1.  REAL-TIME + SIGNED PUB/SUB
────────────────────────────────────────────────────────────────────────────────

COVERED:
- HMAC verify gate at the Redis subscriber: verifyWsHmac is called exactly
  once in apps/api/src/realtime/redis.service.ts:137 in handleRedisMessage —
  unverified messages on tenant:* / group:* / device:* are dropped BEFORE
  fan-out. CLAUDE.md's safeguard claim traces cleanly to the call site.
- WebSocket gateway preserves the SIGNED envelope's timestamp through to the
  player (the 2026-05-26 P0-1 fix): realtime.gateway.ts:266-274. The previous
  bug where send() rewrote ms→s and the player's freshness gate dropped every
  signed event is fixed.
- Per-eventId dedup at every layer:
    * server signer attaches a UUID eventId (security/websocket-signer.service.ts)
    * player keeps a Map<eventId, Date> with 500-entry cap + 5-min cutoff
      (player/page.tsx:3588-3601)
- Sensitive types properly gated on the player: OVERRIDE, TENANT_CHANGED, SOS,
  TEXT_BROADCAST, MEDIA_ALERT, ALL_CLEAR_MESSAGE — all require signature +
  freshness + dedup (player/page.tsx:3568-3601).
- ALL_CLEAR life-safety fix: forged ALL_CLEAR can't cancel a real lockdown —
  player re-fetches the manifest as the source of truth (player/page.tsx
  ~3603-3617). Server-side, the Redis gate would already drop a forged
  ALL_CLEAR before it reached the player.
- SSE controller fallback wired (realtime/sse.controller.ts) with device-JWT
  auth + revocation check + tenant binding.
- HTTP polling backstop via /screens/:id/manifest carrying the live emergency
  field; manifest-hot-cache busts on every trigger/all-clear.
- Hold-to-trigger UX consistency: 3-second HOLD_DURATION_MS in panic page
  (apps/web/src/app/panic/page.tsx:31); same HOLD_MS in broadcast
  (apps/web/src/app/[schoolId]/emergency/broadcast/page.tsx:33).
- @AllowPanicBypass + RESTRICTED_VIEWER hard-block:
  auth/rbac.guard.ts:66-75 — even if canTriggerPanic is somehow set,
  RESTRICTED_VIEWER can never trigger an emergency.

GAPS:
- P1 — Player's signature field is checked-for-presence only; the actual
  HMAC isn't verified client-side. This is documented as "primary safeguard
  is the server-side gate." Acceptable for v1, BUT: if a router downstream
  of redis.service.ts (e.g., a future SDK plugin or a misconfigured replica)
  ever sends an UNFILTERED message bypassing the gate, the player would
  accept it. Recommend slating per-tenant Ed25519 (CLAUDE.md mentions it as
  a follow-up).
  → Fix: ship the Ed25519 pair-time key issuance in V2 Phase 1 schema-freeze
    work. Tracked in CLAUDE.md Sprint 12+ already.

- P2 — RedisService.sismember has a fail-open posture for JWT-revocation
  checks when Redis is DOWN (redis.service.ts:172-183 returns false). For
  WebSocket auth (realtime.gateway.ts:131-140) this is fail-CLOSED in
  production; for general JWT auth via jwt-auth.guard.ts the same pattern
  applies. Confirm both call sites have the same posture under load.
  → Spot-check: grep jwt_revoked_list across apps/api/src — confirm every
    revocation path is fail-closed in prod.

LENSES:
- DESIGN A — system reads as life-safety serious (signed messages, audit
  trail, hold-to-trigger).
- UX B — operator can pull the trigger in <5s on the panic page; admins
  testing on a phone may want pre-saved scenarios (Sprint 8b backlog).
- FUNCTIONALITY A- — only deduction: full per-tenant asymmetric verify is
  documented follow-up.

§3.  AI PROVIDERS — Anthropic × OpenAI × Google
────────────────────────────────────────────────────────────────────────────────

COVERED:
- Three providers wired via single dispatchAi() entry
  (apps/api/src/ai/ai-providers.ts:289-417). Each provider correctly:
    * uses AbortSignal.timeout(15_000) — no hung-fetch DoS
    * preserves authentication via header (not URL key for Google — fix B1)
    * redacts key=... substrings in error bodies (B1 belt-and-suspenders)
- Test-on-save AND generate-time both call mapProviderQuotaError() — single
  source of truth for "out of credit vs rate-limited" disambiguation
  (ai-providers.ts:452+). Covers:
    * OpenAI 429 + insufficient_quota
    * Anthropic 402 / 400 + credit_balance_too_low
    * Google 429 + RESOURCE_EXHAUSTED (with explicit caveat about minute
      vs daily ambiguity)
- BYOK key encryption via openAiKey() in ai/ai-key-cipher.ts — AES-GCM with
  the device secret as KEK.
- Platform free-tier usage accounting persisted in tenant row
  (aiPlatformUsageMonth + aiPlatformUsageCount) — survives pod restart;
  documented race window (1-call undercount on month-rollover) is bounded
  to one event per tenant per month and explicitly accepted in ai.service.ts.
- Per-tenant failure cap (200/hr) separate from success cap (30/hr) so a
  401-burning malicious tenant can't poll forever without rate-limit.
- Model catalog (ai-providers.ts:200+) — 3 tiers per provider, model IDs
  validated via isKnownModel() / defaultModelFor() → unknown saved models
  fall back to provider default rather than 404.
- Audit-log row on success AND failed key test (per CLAUDE.md "Audit-Fix"
  comments) — verified in ai-key.controller.ts.

GAPS:
- P2 — Anthropic prompt caching (ephemeral cache_control) is supported by
  the provider but NOT used. Our system prompts are 200-500 tokens and
  consistent across calls — caching them would save ~$0.0002/call. Tiny
  spend, but the architecture is documented in CLAUDE.md §3.
  → Fix: add cache_control: {type: 'ephemeral'} to the system field in
    ai-providers.ts:322. 5-min cache TTL covers most operator sessions.

- P2 — Temperature parity across providers: dispatchAi() uses 0.7 only for
  Google (ai-providers.ts:390 generationConfig.temperature); Anthropic and
  OpenAI use provider defaults. Set explicitly across all three for
  consistent output.

LENSES:
- DESIGN A — clean catalog, "Standard / Balanced / Premium" tiers, cost
  per call surfaced in the UI.
- UX A — paste key, click Test, see READY in 2s. Generate sparkle button
  surfaces the right message on quota.
- FUNCTIONALITY A — verified by reading the dispatch + error mapping; no
  obvious holes.
